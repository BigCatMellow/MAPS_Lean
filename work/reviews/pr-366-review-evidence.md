REQUEST_CHANGES: dropping the NIST-beacon step, not just the secret, removes a distinct security property the note never names as lost. Re-read `TARGET-WORK-SAMPLING-MANIFEST.md`'s current "Non-derivable deterministic selection" section directly (lines 109-230, not paraphrased): the beacon's own stated purpose there is *"This commit/beacon construction prevents protocol modifiers from reconstructing the sample AND prevents the curator from deliberately choosing a seed after the public pulse without breaking the earlier secret commitment"* -- i.e. the beacon pulse supplies genuinely-not-yet-existing entropy at commitment time, which is what stops the party computing the selection from privately trying candidates and keeping only a favorable one ("the curator may not choose among available pulses after seeing resulting samples" is explicitly forbidden by name). The secret stops an *outsider* from reproducing the result; the beacon stops the *insider* from grinding over results before committing. These are two independent properties. PR #366's proposal (`work/notes/2026-09-15-pr341-custody-descope-design.md` §3.1) drops both the secret AND the beacon, replacing the seed with `SHA256(fixed-namespace-string + already-public-and-frozen-inputs)` -- every byte of that formula's output is something the operator (or anyone) can compute entirely offline, with zero footprint, before ever writing anything to git, since the pool is frozen and public before the rule is chosen. Nothing in the design prevents privately dry-running the proposed formula, or any number of textually-different-but-equally-'reasonable' variants of it (different namespace string, field order, casing, delimiter, hash function), against the already-known frozen pool, and only 'pre-registering' (§3.2 step 1) whichever variant yields the most favorable 48-case selection -- presented as though it were the one obvious/principled choice. §3.3's tamper-evidence argument ("a silent post-hoc swap... is visible, dated, attributable in git history") does not apply to this: grinding happens entirely *before* the first git commit and leaves no trace the git-history-divergence check could ever see. §4's residual-risk section explicitly scopes itself away from this ("nothing stops them from then subtly tuning the MAPS_L protocol -- not the case list -- toward whatever the known 48 cases will reward" -- protocol-tuning-after-a-fixed-list, not case-list-selection-itself) and §8.1's own adversarial check only asks whether new candidates could be added to the pool after seeing the rule (answer: no, correctly) -- it does not ask the converse (whether the rule itself could be chosen, from among several equally-defensible variants, to fit an already-known pool), which is the actual gap. This means §0's operator self-attestation ("self-attests they will not tune case selection toward favorable outcomes") was not given this specific attack surface to accept or reject -- per the note's own stated principle in §4 ("a materially more honest thing to record than silently weakening the design without naming what was lost"), this vector should be named for the operator explicitly, not left implicit. Concrete fix directions that would close this without reintroducing a custodian (not applied here, this is a review not an edit): (a) require the exact formula text to be pre-registered before `source_pool_definition_sha256`/`approved_design_head` exist or are known to the operator (impossible here, since both are already-frozen prerequisites per the note's own §3.1), or (b) retain some externally-generated, not-yet-existing-at-registration-time public entropy (e.g. a future git commit's own SHA from an unrelated, contemporaneously-pinned external repository/timestamp service, or literally keep the NIST beacon pulse as the only namespace-differentiating input, dropping only the *secret* half of the original scheme while keeping the *beacon* half) -- the note conflates "we don't need secrecy since there's no custodian to protect" with "we don't need any external unpredictability at all," but only the first claim is actually supported by the solo-owner constraint the operator's authorization describes.
