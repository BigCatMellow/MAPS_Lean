## Findings

### Finding 1 — non-blocking, factual accuracy in the note's cost argument

`work/notes/2026-08-26-worktree-binding-enforcement-seam-design.md:150` states that "`collect_git_worktree_identity()` is a single `git rev-parse` invocation". It is not. `runtime/integrity/git_scope.py::collect_git_worktree_identity()` lines 65-95 spawn five separate Git subprocesses: `rev-parse --show-toplevel`, `rev-parse --git-common-dir`, `rev-parse --git-dir`, `rev-parse --git-path .`, and `rev-parse --verify HEAD^{commit}`. The comparative conclusion still holds directionally — the full `verify_git_run()` path costs roughly nine subprocesses on a bound run — but "single invocation" understates per-send cost by 5x and should be corrected in the follow-up rather than carried forward as a design premise. The decision itself does not depend on this claim: hazards 1 and 2 (authority breadth and unbound-run compatibility) are sufficient on their own.

### Finding 2 — non-blocking but material, the "already enforced" contrast overstates

The note's §"Contrast: the sibling verifier is already enforced" (lines 44-57) and the task's goal line ("make an existing production dispatch guard fail closed") both imply `CanonicalRunGuard` sits in a live dispatch path. In this repo it does not sit in any composed one. `grep -rn "register_canonical_run_guards\|CanonicalRunGuard"` finds non-test occurrences only in the definition (`runtime/policy/harness_guard.py`) and the re-export (`runtime/policy/__init__.py`); every registration call site is a test (`tests/test_agentic_security_hook_context.py:104`, `tests/test_recovery_supervisor.py:766`, `tests/test_harness_service.py:156`, `tests/test_agentic_security_baseline.py:194,205`, `tests/test_harness_canonical_guard.py:277,287,300`). Likewise `grep -rn "HarnessService("` finds instantiations only in tests. `runtime/harness/service.py::_require_canonical_enforcement()` does make the guard mandatory *once a `HarnessService` is composed*, so the guard is fail-closed by construction — but no in-repo composition root exists, so the enforcement layer is library-only today.

Consequence: `check_run_stale()` is enforced in a *stronger structural sense* than `verify_git_run()` (mandatory when composed, versus reachable only on explicit CLI request), which is a real and correctly identified asymmetry — but it is not enforced in a *running* production dispatch flow, because there isn't one in this repo. The follow-up task must not, on completion, claim E6's "enforcement of the binding in a dispatch flow" gap is closed; completing it closes the *guard-layer* gap and leaves the composition-root gap open. Recommend the follow-up task record this distinction explicitly in its evidence labels before it is dispatched, so the E6 row is not promoted on it. This is not blocking for a design note that marks nothing DONE.

### Finding 3 — minor, precision on where `RUN_STALE` actually applies

The note's bullet at lines 51-53 lists all four registered events immediately after describing the `RUN_STALE` deny, which reads as if the stale check runs at each. `CanonicalRunGuard.__call__` gates `_require_current_run()` behind `continuing` (`start`/`send`/`resume`) only — `stop` is session-bound but not continuing. The note's own §3 and §4 get this right, so this is phrasing in the contrast section, not a design error.

### Judgment — design note first, or direct wiring?

Asked to judge rather than only fact-check: **design-note-first was defensible here, but generous.** The implementation the note prescribes is small — extract `compare_worktree_identity()`, add one injectable constructor parameter, add `_require_bound_worktree()` with three branches, and six tests. Call it forty lines plus coverage. Against that, the note's own hazards are real and non-obvious: naively calling `verify_git_run()` from `BEFORE_SEND` would have imported changed-path denial authority into a mandatory guard, which is a genuine authority expansion that E6's checklist row disclaims, and `work/tasks/run-worktree-binding.md:71` does reserve exactly this class of decision for the owner. A reviewer who saw the naive wiring in a PR would have been right to reject it, so the note bought something real.

What it costs is a full independent-review cycle for a document nobody disputes, and this is the third design artifact in the same arc (`2026-08-24-worktree-run-binding-design.md`, then the #156/#157 implementation pair, now this). My honest view is that the identity-only guard could have shipped as one PR with this note's §"Decision" as the PR body — the escalation triggers are satisfied by *stating* that unbound runs are allowed and `SESSION_STOPPING` is untouched, which is a design commitment reviewable in the same diff that implements it. I record this as a process observation, not a defect: the note is accurate, bounded, marks nothing DONE, and leaves the tree in a strictly better-documented state, so there is nothing here to reject. If a fourth design note precedes the next small change in this arc, that pattern should be examined.
