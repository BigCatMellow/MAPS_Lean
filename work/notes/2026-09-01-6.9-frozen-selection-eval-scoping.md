## 1. The exact acceptance bar (dispatch Q1)

### 1a. What §6.9 actually says

`work/roadmaps/00-MASTER-MAPS-CAPABILITY-ROADMAP.md` §6.9 (the whole section,
lines ~2185–2215):

- **"Routing evaluation must include"** — `direct matches; paraphrases;
  vocabulary shifts; overlapping Skills; hard negatives; no-Skill cases`
  (six categories).
- **"Promotion gate"** — one line: *"Do not rely on fuzzy Skill selection
  without a frozen selection evaluation."* (line 708 — same sentence.)

That is the **entire** 6.9 gate. It is a **coverage + existence** bar, not a
numeric-threshold bar: a frozen eval must *exist*, must *cover the six
categories*, and fuzzy selection must not be relied on without it.

### 1b. The "meaningful improvement over baseline" language is NOT the 6.9 gate

Lines 1383, 1961, 796 all say variants of *"must demonstrate meaningful
improvement over explicit/baseline context composition"* / *"Semantic retrieval
must outperform explicit-first context on frozen paraphrase/hard-negative
evaluations"*. **Read in context these are the L4 / EXP-B *semantic-retrieval*
gate**, not the 6.9 Skill-selection gate:

- line 796 is under the retrieval-methods guardrail;
- line 1961 is literally *"Semantic retrieval must outperform explicit-first"*;
- line 1383 is in the retrieval-experiment section.

`runtime/context_builder.py::_select_skills` is **already explicit-first** —
exact `_text_tokens(name) | _text_tokens(description)` ∩ task-signal tokens
(`task_type` / `project_id` / output-path segments), no fuzzy/semantic match.
There is **no "baseline"** for it to beat: it *is* the explicit baseline. A
"beat the baseline by X" bar has no meaning for the current selector; it would
apply only to a *future* semantic selector, which is L4/EXP-B's problem, not
6.9's.

### 1c. Is there a pre-registered number? **No.**

`tests/test_exp_a_skill_routing.py:187-219` asserts the **exact current EXP-A
numbers** as a *regression pin*, not a bar:

```
report.total_cases == 12; missed_activation_cases == 1; false_activation_cases == 1;
exact_cases == 10; exact_rate == 10/12;
0.0 < selection_precision < 1.0; 0.0 < selection_recall < 1.0
```

The test's own docstring (`:164-177`): *"these assertions pin the current
behaviour … update the assertions only alongside a deliberate, reviewed
selector change"*. It is a change-detector, not a promotion criterion. **No
`>= X` threshold exists anywhere** (`/usr/bin/grep -rn "threshold\|promotion.*gate\|>= 0\." runtime/ tests/`
→ nothing for skill selection).

**Defining the bar is part of the future work** — and §1e says whose call it is.

### 1d. What "the bar" should be (proposed, for the reviewer/operator to set)

A defensible promotion criterion for the current explicit selector, expressed
against the harness's existing `SkillSelectionEvalReport` fields
(`runtime/skills/evaluation.py:150-186` — `selection_precision`,
`selection_recall`, `selection_f1`, `exact_rate`, `false_activation_cases`,
`missed_activation_cases`, `ambiguity_accuracy`, per-category correctness):

1. **Coverage**: ≥ N cases in *each* of the six §6.9 categories (proposal:
   N = 4, ~26 cases total).
2. **No category collapses**: per-category `exact` rate ≥ some floor in every
   category (so the selector isn't carried by DIRECT cases).
3. **Hard-negative / no-Skill discipline**: `false_activation_cases` on
   `HARD_NEGATIVE` + `NO_SKILL` cases ≤ some small count (the safety-relevant
   direction — surfacing an irrelevant Skill is worse than missing one, given
   the trust gate downstream).
4. **Aggregate**: `selection_f1 ≥ <bar>` on the full corpus.

The **numbers in `<…>`** are the review/operator judgment (§1e). This note
proposes the *shape*, not the values.

### 1e. Whose call is the bar — **REVIEW/OPERATOR** (dispatch Q5, answered here)

Roadmap §6.9 task-list, line 1754: *"7. **review/operator** promotion gate"*.
Line 2167: *"- measured promotion gate"*. §6.9's own "Promotion gate" heading.

Setting the numeric floors in §1d — and deciding whether the characterized
behaviour clears them — is explicitly a **review-or-operator** judgment, not an
implementer one. The dispatch's MUST-NOT ("do not set the promotion threshold
yourself if you conclude it's an operator call") applies: **this note does not
set the bar.**

Whether it is *operator*-level or *reviewer*-level: the roadmap says
"review/operator", i.e. either suffices. Recommendation — a **reviewer** can set
and apply the §1d floors *if* the operator has not signalled otherwise, because
(a) it is a quality bar on an already-approved capability, not a scope/authority
question, and (b) the trust gate (6.22) and the SEC4 quarantine already sit
downstream of selection, so a mis-selection is contained. **If the operator
wants to hold the bar themselves, that is their call to make — flag it in the
impl PR, don't assume.**

## 2. What exists vs. what's missing (dispatch Q2)

### 2a. Exists — and it is real end-to-end

| Piece | Where | State |
|---|---|---|
| The eval harness | `runtime/skills/evaluation.py` — `SkillSelectionCorpus`, `SkillSelectionCategory` (8 members incl. all 6 roadmap categories + `NEAR_MISS`, `AMBIGUOUS`), `evaluate_skill_selection(corpus, predictions) -> SkillSelectionEvalReport` (precision/recall/f1/exact/false-activation/missed-activation/ambiguity + per-category) | **DONE** (S4, PR #27) |
| The live selector | `runtime/context_builder.py::_select_skills` — explicit token-intersection | **DONE** (S6, PR #109; unchanged by 6.9 slices 1/2 — they add loading, not selection) |
| A frozen corpus + a run wiring the two | `runtime/skills/eval_corpora/exp_a_skill_routing_v1.json` (12 cases) + `tests/test_exp_a_skill_routing.py` — builds a real `SkillCatalog` from on-disk `SKILL.md`, runs the **real** `_select_skills` through the **real** `evaluate_skill_selection`, no stubs | **DONE** (L4/EXP-A) — results `work/notes/2026-08-19-exp-a-skill-routing-benchmark.md` (precision 0.889, recall 0.889, 10/12 exact, 1 false + 1 missed activation) |

**EXP-A already IS a frozen selection evaluation of the production selector.**
That is most of the 6.9 gate.

### 2b. Missing — the gap between "EXP-A done" and "6.9 gate met"

1. **Category coverage.** EXP-A's 12 cases (verified via `json` +
   `Counter`): `DIRECT 5, HARD_NEGATIVE 2, NO_SKILL 2, PARAPHRASE 1,
   VOCABULARY_SHIFT 1, MULTI_SKILL 1`. Against §6.9's six required categories:
   - direct matches — ✓ (5)
   - paraphrases — **thin** (1)
   - vocabulary shifts — **thin** (1)
   - overlapping Skills — **thin** (1 `MULTI_SKILL`; 0 `AMBIGUOUS`)
   - hard negatives — ✓ (2)
   - no-Skill cases — ✓ (2)
   A single case in a category is a demonstration, not an evaluation.
2. **A stated promotion criterion.** §1c — none exists. §1d proposes the shape;
   §1e says the values are a review/operator call.
3. **The run recorded as a gate decision.** EXP-A's numbers live in a dated
   note as a *benchmark result*. The 6.9 gate wants a
   `frozen-eval: PASS (criterion X, reviewer/operator Y, date Z)` record — a
   checklist evidence clause + a note, produced *after* §1d/§1e land.
4. **(nice-to-have, not required by §6.9)** `NEAR_MISS` and `AMBIGUOUS`
   coverage — the harness supports both; §6.9 does not list them, but a serious
   selection eval should include near-misses.

**The gap is corpus-authoring + criterion-setting + one run + one record.** Not
selector work, not harness work, not a retrieval experiment.
