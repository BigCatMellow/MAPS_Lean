## 1. Re-verified primitive inventory

### 1a. Three distinct lineage surfaces exist — the scoping note conflated two of them

| Surface | Primitive | Grain | Purpose |
|---|---|---|---|
| `continuity_links` | `record_continuity_link(predecessor_id, replacement_id, *, reason)` (`runtime/state/integrity.py:479`) | **identity → identity** | drives review-independence: `_continuity_component_conn` walks it, and `claim_review` / `record_review` / `review_binding` / `policy` reject a reviewer in the submission author's component |
| `run_recovery_links` | `record_run_recovery_link(predecessor_run_id, replacement_run_id, …)` (`runtime/state/helper_recovery_lineage.py:249`) | **run → run, SAME task** | records a recovery replacement run; **rejects a cross-task link** (`RECOVERY_TASK_MISMATCH`), requires **both runs to already exist** |
| `run_helper_links` | `record_run_helper_link(run_id, helper_run_id, …)` | run + helper-invocation id | within-run helper invocations; requires the caller be the run's ACTIVE claimant with a live lease |

**Correction to the scoping note (§1c):** it named `record_run_helper_link` /
`record_run_recovery_link` as handoff's "continuity link" surface and assumed
"a replacement task is `create_task` + `update_contract`". Re-verification shows:

- The review-independence consequence is driven by **`continuity_links`
  (identity→identity)** — *not* the run-lineage tables.
  `test_agentic_security_baseline.py::test_sec_adv_006` proves it:
  `record_continuity_link("author", "helper-continuation", …)` then
  `claim_review(task, "helper-continuation")` → `CONTINUITY_REVIEW_FORBIDDEN`.
- `record_run_recovery_link` **cannot** link to a fresh replacement *task* —
  both runs must share `task_id` (`RECOVERY_TASK_MISMATCH`) and both must
  already exist. There is **no cross-task lineage primitive**. A `flow handoff`
  that mints a new task would need one → that framing is out.

### 1b. There is no claim-release / claim-transfer primitive for a LIVE claim

`runtime/state/execution.py::claim_task` (lines 11–101): a second worker can
take over an `ACTIVE` task **only** when `recover=True` — which requires the
lease to be **expired** (`lease is None or lease > current` → `LEASE_ACTIVE`
otherwise) **and** `attempt < max_attempts` (`ATTEMPT_LIMIT` otherwise), and it
bumps `attempt`. `/usr/bin/grep -n "def release\|def unclaim\|def abandon\|def
reassign\|claimed_by = NULL" runtime/state/*.py` → the only `claimed_by = NULL`
is inside `submit_task` (→ `READY_FOR_REVIEW`). **No voluntary claim release
exists** (same gap as `recover`, scoping note §1a).

### 1c. `flow start` / `flow review-start` stop-boundary precedent

`runtime/flow_start.py:172` returns
`next_step: {"state": "STOPPED_BEFORE_PROVIDER_SESSION", "reason": "flow start
does not select workers, launch providers, attach sessions, or send messages"}`.
`runtime/flow_review.py::flow_review_start` returns
`next_step: {"state": "STOPPED_BEFORE_REVIEW_VERDICT", …}`. Both are pure
compositions over guarded store ops that **stop before the next actor acts**
(`flow start` stops before session launch; `flow review-start` stops before a
verdict). `flow_review.py` provides the reusable `_failed` / `_mutation_payload`
helpers.

### 1d. `continuity_links` schema

`runtime/state/schema.sql:516` — `(predecessor_id, replacement_id, reason,
created_at)`, `PRIMARY KEY(predecessor_id, replacement_id)` (so a duplicate
link is idempotent-rejected as `CONTINUITY_CONFLICT`), `CHECK(predecessor_id <>
replacement_id)`. `record_continuity_link` has **no authority check** — it is a
low-level integrity primitive.

## 2. The stop boundary

Applying the `flow start` precedent (stop before the next actor acts), a scoped
`maps flow handoff` **stops after recording the continuity link and before the
incoming worker claims**. It emits a continuity link + the facts the incoming
worker needs; it does **not** claim-recover the task, bind a replacement run
manifest, select the incoming worker, or launch a session.

### `flow handoff` is SAME-TASK

Because continuity is identity→identity and there is no cross-task lineage
primitive (1a), `flow handoff` does **not** create a replacement task. The
*same* task T is continued by a different worker identity via the existing
claim-recovery path. The verb's job is to record — before that happens — that
worker B is a continuation of worker A, so B inherits A's review-independence
disqualification for T's lineage.

### Emitted `next_step`

```json
{
  "state": "STOPPED_BEFORE_REPLACEMENT_CLAIM",
  "reason": "flow handoff records the identity continuity link and its
    review-independence consequence; the incoming worker must still claim-recover
    the task after the outgoing lease expires (maps claim / maps flow start) and
    bind its own run manifest; no worker is selected and no session is launched"
}
```

matching the `{state, reason}` shape `flow start` / `flow review-start` use (and
which the pending 6.21 increment (a) formalizes across the family).

## 3. State-change semantics

### What changes: exactly one `continuity_links` row

`flow_handoff` in its smallest form is a **pure composition over one existing
primitive** — `record_continuity_link(outgoing_worker_id, incoming_worker_id,
reason=…)`. Nothing else in task / lease / claim / review / run state is
mutated.

### What does NOT change (and why that is correct)

- **The outgoing claim is untouched.** There is no release primitive (1b), and
  `flow handoff` must not add one. The outgoing worker's lease expires
  naturally (or is allowed to lapse); the incoming worker then uses the
  existing `claim_task` recovery path (`LEASE_EXPIRED` → `recover=True`,
  `attempt += 1`). Recording the continuity link **before** the lease expires
  is harmless — the link is simply in place early.
- **Nothing is "frozen".** The roadmap's "freeze current state/context" step is
  already satisfied structurally: the outgoing run manifest is immutable
  (`run_manifests` has no update path), and the task revision is content-
  addressed. `flow handoff` records the **outgoing `run_id`** in its output as
  the handoff point, but freezes nothing new.
- **The replacement does NOT inherit the contract via `update_contract`.** Same
  task → same contract already. (`update_contract` is status-frozen for an
  `ACTIVE`/`READY_FOR_REVIEW` task anyway — `runtime/state/base.py`
  `CONTRACT_FROZEN`.)
- **No replacement run manifest.** That is bound by the incoming worker's own
  `maps flow start` after it claims — explicitly past the stop boundary.

### Composition guard (not new authority)

`flow_handoff` should verify the caller is entitled to declare the handoff:
the **outgoing worker must currently hold the claim** (task `ACTIVE`,
`claimed_by == outgoing_worker_id`). This mirrors `flow_review_record` letting
`record_review` enforce ownership — here the flow checks it directly against
`store.get_task(task_id)` before calling `record_continuity_link` (which has no
check of its own). An operator-initiated handoff of an abandoned task is a
follow-up (it overlaps `recover`, §5).

### Optional richer variant — DEFERRED

Once the incoming worker's replacement run exists, a
`record_run_recovery_link(outgoing_run_id, incoming_run_id, …)` could record
run→run continuity too (same task, so no `RECOVERY_TASK_MISMATCH`). But that
run does not exist at `flow handoff` time (chicken/egg) — it is a step for the
incoming `flow start` or a follow-up verb, not slice 1. Noted, deferred.

## 4. The review-independence consequence — automatic, confirmed

Recording `continuity_links(outgoing, incoming)` **is** the review-independence
consequence. Verified against merged code:

- `record_review` (`runtime/state/review.py:169`) and `claim_review` (`:53`):
  `disqualified = self._continuity_component_conn(conn, submission["author_id"])`
  then reject `reviewer_id in disqualified` (`CONTINUITY_REVIEW_FORBIDDEN` /
  `SELF_REVIEW_FORBIDDEN`).
- `_continuity_component_conn` (`runtime/state/integrity.py:520`) transitively
  closes over every `continuity_links` row.
- `review_binding.py:171` and `policy.py:131` apply the same check on the
  approval path.

So after `flow handoff`, if the incoming worker submits task T and the outgoing
worker (or anyone in the outgoing worker's component) tries to claim T's
review, it is refused — with **no further action by `flow handoff`**. The verb
does not touch the review tables; the consequence falls out of the existing
component walk. This is exactly `test_sec_adv_006`'s guarantee, reached through
a `flow` verb instead of a raw `record_continuity_link` call.

**`flow handoff` must NOT** additionally try to pre-disqualify or annotate any
review — the component walk is the single source of truth (rule 12).

## 5. Operator / authority decision?

**None.** Walked through every candidate:

- **Recording a continuity link** is conservative — it only ever *removes*
  review eligibility, never grants capability or authority. `record_continuity_link`
  is un-gated today and used un-gated by `test_sec_adv_006`.
- **The composition guard** (§3 — caller must hold the outgoing claim) is a
  read of existing task state, not a new authority.
- **The claim transfer itself** uses the unchanged `claim_task` recovery path,
  which already has its own guards (`LEASE_EXPIRED`, `ATTEMPT_LIMIT`).
- **Who may be the incoming identity** — any identity; the `continuity_links`
  PK + `CHECK` already reject self-links and duplicates; merging B into A's
  component has only the (intended, conservative) review-disqualification
  effect.

`flow handoff` is therefore **DISPATCHABLE** as a design-decision-only slice.
`recover` and `release` stay **PARKED** (scoping note §1a / §1b — `recover`
needs an operator decision + `reviews`-schema decision; `release` needs its own
multi-step design note).

## 6. Smallest first slice

**Property made true:** `maps flow handoff TASK --from-worker A --to-worker B
--reason "<why>"` records `continuity_links(A, B)` — provided task T is `ACTIVE`
and claimed by A — and returns a deterministic `next_step` telling the operator
that B must now claim-recover T. After it, B cannot claim independent review of
T's lineage and neither can anyone in A's continuity component.

### Impl surface (Phase 2 — NOT this note)

1. **`runtime/flow_handoff.py`** (new, ~60 lines, mirrors `flow_review.py`):
   `flow_handoff(store, task_id, *, from_worker, to_worker, reason)`:
   - `task = store.get_task(task_id)`; fail `_failed("preflight", …)` if `None`,
     if `status != "ACTIVE"`, or if `claimed_by != from_worker`

   - return `{"ok": True, "code": "FLOW_HANDOFF_RECORDED", "task_id", "from_worker",

## 7. Out of scope

- **`recover`** — force-closing another identity's open review; needs an
  operator decision (who, on what trigger, with what audit outcome) + a
  `reviews`-schema decision (released/abandoned state vs. row deletion).
  Stays PARKED (scoping note §1a).
- **`release` (`flow release-check`)** — needs its own design note for the three
  new checkable steps ("artifact identity validation", "release-path smoke",
  "operator-visible summary" sink) — none is a composition over an existing op.
  Stays PARKED (scoping note §1b).
- **Actual claim transfer / lease release** — `flow handoff` stops before it;
  the incoming worker uses the unchanged `claim_task` recovery path after the
  outgoing lease expires. An operator-forced release of a live claim is a
  `recover`-adjacent decision, not this slice.
- **Provider session launch / worker selection** — excluded by the `flow start`
  precedent.
- **`record_run_recovery_link` between the two runs** — deferred (the incoming
  run does not exist at handoff time; §3).
- **A cross-task handoff** (new task + cross-task lineage) — would need a new
  lineage primitive; not this design, and likely never (the same-task model is
  sufficient).

## 8. STOP-condition check (dispatch)

- *Needs a new store primitive or schema change?* — **No.**
  `record_continuity_link` exists and is the whole state change; everything else
  is reads (`get_task`) + the existing `claim_task` recovery path (past the stop
  boundary). No `schema.sql` touch.
- *Operator authority decision blocks the smallest slice?* — **No** (§5).
- *Stop-boundary question has no clean answer without deciding provider-launch
  policy?* — **No.** The `flow start` precedent gives a clean answer: stop
  before the next actor acts (here: before the incoming worker's claim). Provider
  launch is already, separately, out (same as `flow start`).

No STOP condition triggered. `flow handoff` is dispatchable as slice 1.
