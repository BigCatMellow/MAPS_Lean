## 2. Re-verified facts — where Skill loading stands today

### 2a. The 6.9 target (MASTER roadmap `00-MASTER-MAPS-CAPABILITY-ROADMAP.md` §6.9, lines ~684-694)

```
startup    → Skill name/description metadata only
activation → full SKILL.md
execution  → scripts/references/examples only if needed
```

S6 exit gate (`agent-harness-capabilities/02-procedural-knowledge-and-skills.md:684`):
"unrelated Skills demonstrably stay out of context."

### 2b. Current state = the "startup" level only

- `runtime/context_builder.py::_select_skills` (lines 328-413) — for each
  catalog entry whose `descriptor.name`/`descriptor.description` tokens
  intersect the task signal tokens (`task_type`, `project_id`, output-path
  segments), emits a dict of **metadata only**: `skill_id`, `name`,
  `description`, `source_id`, `lifecycle_state`, `trust_class`,
  `selection_reason`, `catalog_key`, `budget_class`, and `withheld_reason`
  when applicable (lines 390-411). Its own docstring (lines 335-338):
  "`load_skill`/`load_catalog_skill` (procedure body activation) is never
  called, so no Skill instruction text can enter the plan."
- The trust gate (roadmap 6.22) already runs here: `admit_memory_evidence(
  trust_class, …)` (line 380). `MemoryAdmission.LOAD` → `budget_class =
  _BUDGET_SHOULD_LOAD` (lines 404-406); `WITHHOLD` → `_BUDGET_ON_DEMAND` +
  `withheld_reason` (lines 407-411); `DENY` → entry dropped and counted
  (lines 387-389). A `None` lifecycle state (every Skill with no durable
  subject row) projects to `OBSERVATION` → `WITHHOLD` — so today an
  unassessed Skill is already emitted as `ON_DEMAND` metadata, not in the
  default load set.
- `build_context_plan` (line 415) calls `_select_skills(skill_catalog, task)`
  at line 533 and puts the result at `plan["skills"]` (line 548). It has
  `store` as a parameter (line 416) but **does not pass it to
  `_select_skills`** — `_select_skills` receives only the `SkillCatalog`.
- `runtime/flow_start.py` (`maps flow start`) is the only caller that passes a
  real catalog: `build_project_skill_catalog(repo_root, store)` (line 118)
  then `build_context_plan(store, task_id, repo_root=repo_root,
  skill_catalog=skill_catalog)` (lines 124-126). Its docstring (lines
  108-109): "No Skill procedure body is loaded -- only descriptor/provenance
  metadata."
- `runtime/cli.py:537` (`maps context`) calls `build_context_plan(store,
  args.task_id, repo_root=args.repo_root)` with **no** `skill_catalog`, so
  `_select_skills(None, task)` returns `[]` immediately (line 360). `maps
  context` is unaffected by anything in this design.

### 2c. The activation primitive already exists and is unused from context building

- `runtime/skills/catalog.py::load_catalog_skill(entry, store=None)` (lines
  306-334) — "Activate exactly the catalog entry selected by the caller.
  Catalog lookup does not authorize activation." When `store` is given it is
  "the first real refusal wired to the durable lifecycle state (SEC4 Half
  2)": raises `SkillCatalogError` if the composed state is `QUARANTINED` /
  `RETIRED` / `SUPERSEDED` (lines 326-332); `APPROVED` / `ACTIVE` /
  `VALIDATED` / `None` pass through. Returns `load_skill(entry.descriptor)`
  (line 334).
- `runtime/skills/format.py::load_skill(descriptor)` (lines 309-353) —
  `_verified_snapshot(descriptor)` re-hashes the discovered directory
  "immediately before reading the procedure body" and raises
  `SkillChangedError` on any drift in identity/resources. Returns
  `SkillDocument(descriptor=current, body=body)` where `body: str` is the
  SKILL.md content below the frontmatter (`format.py` lines 47-52).
- `SkillCatalogEntry` (`catalog.py` lines 96-102) carries `descriptor`,
  `provenance`, and a `catalog_key` property — everything `load_catalog_skill`
  needs.
- `/usr/bin/grep -rn "load_catalog_skill\|load_skill(" runtime/ | grep -v test`
  → the only non-test callers are `catalog.py` (internal) and the `maps skill`
  CLI verbs; **nothing in the context-building path calls either.**

### 2d. What is NOT the gap

- Selection / routing is done (S4 eval corpus, S6 `_select_skills`,
  EXP-A benchmarked). The gap is purely *loading the selected Skill's body*.
- The trust/lifecycle refusal is done (SEC4 Half 2 + catalog entrypoint) —
  `load_catalog_skill(entry, store)` already refuses a QUARANTINED Skill.
- The budget classifier is done (6.11) — `budget_class` already marks which
  Skills *should* load.

The gap is one wire: **nothing calls `load_catalog_skill` for a
LOAD-classified selected Skill and puts its verified body into the plan.**

## 3. The smallest dispatchable slice

### 3a. The one concrete property to make true in a real `maps flow start` run

> In the `maps flow start` context plan, a matched Skill whose trust gate
> decision is `LOAD` (`budget_class == "MUST_LOAD"`/`SHOULD_LOAD`) carries its
> **hash-verified SKILL.md body** at `plan["skills"][i]["body"]`, obtained via
> `load_catalog_skill(entry, store)`. A matched Skill that is `WITHHOLD`
> (`ON_DEMAND`, incl. every unassessed `None`-state Skill) or `DENY` carries
> **no `body` key** — exactly as today. If body activation raises
> (`SkillCatalogError` / `SkillChangedError`), the item is emitted
> metadata-only with `body_withheld_reason` and the plan is not broken.

This advances 6.9 from "startup" to "activation" for precisely the Skills the
existing trust gate already says to load, and no others. The S6 exit gate
("unrelated Skills stay out of context") is *strengthened*: unrelated Skills
were already omitted; now even matched-but-untrusted Skills contribute no body.

### 3b. Implementation surface (for the eventual impl task — NOT this note)

1. **`runtime/context_builder.py`**:
   - Thread `store` into `_select_skills` — change the signature to
     `_select_skills(skill_catalog, task, store)` and pass `store` at the
     line 533 call site. (`store` is already a `build_context_plan` param.)
   - After an item is determined to be `MemoryAdmission.LOAD`, call
     `load_catalog_skill(entry, store)`; on success set `item["body"] =
     document.body` (and optionally `item["body_sha256"] =
     document.descriptor.content_sha256`). On `SkillCatalogError` /
     `SkillChangedError` / `SkillParseError`, set `item["body_withheld_reason"]`
     to a short stable code (e.g. `"BODY_ACTIVATION_FAILED"` /
     `"SKILL_CHANGED"`) and leave the item metadata-only. Never raise out of
     `_select_skills` — its contract is fail-closed (docstring lines 331-333).
   - `WITHHOLD` / `DENY` branches unchanged — no `load_catalog_skill` call.
2. **Plan coverage flags** (`build_context_plan` return, ~line 548-560): add
   `coverage.skill_bodies_loaded` (int) so a reader/test can assert how many
   bodies entered the plan without diffing the list.
3. **`runtime/flow_start.py`**: update the step-2 docstring (lines 100-109)
   which currently states "No Skill procedure body is loaded" — it will now
   load bodies for LOAD-classified Skills only.
4. **Tests** — `tests/test_context_builder.py` (+ a focused
   `tests/test_skill_body_loading.py` if cleaner):
   - a VALIDATED/APPROVED matched Skill → `plan["skills"][i]["body"]` equals
     the real SKILL.md body; `coverage.skill_bodies_loaded == 1`;
   - a `None`-state (unassessed) matched Skill → no `body` key, still
     `ON_DEMAND` with `withheld_reason` (unchanged);
   - a QUARANTINED matched Skill → dropped (unchanged, `load_catalog_skill`
     would refuse but it is never reached because admission is already DENY);
   - a Skill whose directory bytes change between discovery and plan build →
     `body_withheld_reason` set, plan still returned;
   - an end-to-end `flow_start` test (real `build_project_skill_catalog` +
     `build_context_plan`) showing a bundled VALIDATED Skill's body in the
     plan and an unrelated Skill entirely absent.
5. **`work/roadmaps/CAPABILITY_CHECKLIST.md`** rows S6 (line 38), 6.9 (line
   118), and the SEC4 caveat (line 60): one evidence clause each ("progressive
   body loading slice 1: LOAD-classified matched Skills carry a hash-verified
   `body` in the flow-start plan"). **NO status flip** — S6/6.9 stay IN
   PROGRESS: the "execution" level (scripts/references/examples on demand) and
   any byte-budget enforcement (6.11 interaction) remain.

### 3c. MAY / MUST NOT

**MAY touch:** `runtime/context_builder.py` (`_select_skills` signature +
LOAD-branch body call + one coverage counter), `runtime/flow_start.py`
(docstring only), `tests/test_context_builder.py` + one new test module,
`work/roadmaps/CAPABILITY_CHECKLIST.md` (evidence text, no status).

**MUST NOT:**
- change `runtime/state/schema.sql` or any table — the plan is disposable,
  nothing about the body is persisted;
- add any new retrieval / file search / directory walk — the body comes
  **only** from `load_catalog_skill` on an entry `_select_skills` already
  selected (explicit-first Context Builder invariant, 6.11 guardrail);
- load `script_paths` / `reference_paths` / `example_paths` / `asset_paths`
  content — that is the "execution" level, a later slice;
- load a body for any `WITHHOLD` / `ON_DEMAND` / `DENY` Skill, or for a Skill
  with a `None` lifecycle state;
- modify `load_catalog_skill` / `load_skill` / `_verified_snapshot` /
  `admit_memory_evidence` / the trust projection — all consumed as-is;
- change the selection/matching logic or the `budget_class` mapping;
- flip any checklist status;
- touch `maps context` (`cli.py`) — it passes no catalog and stays
  body-free.

### 3d. Acceptance criteria (pass/fail)

1. `_select_skills(catalog, task, store)` with a matched VALIDATED Skill →
   returned item has `body` == the Skill's real SKILL.md body text.
2. Same with a matched `None`-state Skill → item has **no** `body` key,
   `budget_class == "ON_DEMAND"`, `withheld_reason` present.
3. `build_context_plan` for a flow with one matched VALIDATED bundled Skill →
   `plan["coverage"]["skill_bodies_loaded"] == 1`; an unrelated bundled Skill
   contributes zero items.
4. Discovery-then-mutate the Skill dir → `body_withheld_reason` set, plan
   still returned (not `None`, no exception).
5. `maps context` plan (no catalog) unchanged — `plan["skills"] == []`.
6. `python3 -m unittest tests.test_context_builder tests.test_skills_catalog
   tests.test_cli_skill tests.test_flow_start` green (one blocking foreground
   run). `python3 -m runtime.smoke` exit 0.
7. `git diff` touches only the files in §3c "MAY touch".

## 4. Out of scope (later slices)

- **"Execution" level** — on-demand loading of `scripts/` / `references/` /
  `examples/` / `assets/` when the running task actually needs them. Needs a
  demand signal that does not exist yet (the plan is built before any provider
  session runs). Distinct slice.
- **Byte-budget enforcement (6.11 interaction)** — capping total loaded Skill
  body bytes, or demoting `MUST_LOAD` → `ON_DEMAND` under budget pressure.
  `budget_class` does not drive any load/fetch behavior downstream today
  (`CAPABILITY_CHECKLIST.md:120`); wiring that is 6.11's job.
- **Multiple catalog sources** — only one `BUNDLED` source at
  `<repo_root>/.claude/skills/` exists (`build_project_skill_catalog`).
- **Capability Packs (S7 / 6.12)** — gated on S6; body loading is a
  prerequisite, not part of this slice.
- **Provider-session injection** — how a loaded body reaches an actual worker
  prompt. `flow_start` "intentionally stops before choosing or launching a
  provider session"; the plan is the artifact this slice fills.
- **Deduplication / summarization of bodies** — slice 1 loads verbatim.

## 5. OPERATOR DECISION — none required for slice 1

No new authority surface. `load_catalog_skill(entry, store)` **already**
enforces the SEC4 lifecycle refusal, and slice 1 only calls it for Skills the
trust gate has already classified `LOAD` (`VALIDATED`/`APPROVED`/`ACTIVE`) —
a strict subset of what `load_catalog_skill` would permit. The SKILL.md body
is prose already covered by `content_sha256` and already statically linted by
the SEC4/SEC5 gate at catalog-build time (a dangerous body is `QUARANTINED`
and never reaches `LOAD`). The plan is read-only and disposable. No operator
trust-root question is opened.

If the impl surfaces one anyway (e.g. a proposal to load bodies for
`None`-state Skills, or to bypass the trust gate) that is **out of slice 1** —
STOP and ping rozo.

## 6. Recommendation

Adopt §3 slice 1: thread `store` into `_select_skills`, and for a
`MemoryAdmission.LOAD` matched Skill call the existing
`load_catalog_skill(entry, store)` and attach the verified `body` to the plan
item (fail-closed on activation error). One coverage counter, one docstring
fix, tests, one non-flipping checklist evidence clause. It is a genuine
deterministic increment — an existing primitive wired to an existing decision
point — not a Context Builder rewrite, and it moves 6.9 from "startup" to
"activation" for exactly the Skills already trusted to load.
