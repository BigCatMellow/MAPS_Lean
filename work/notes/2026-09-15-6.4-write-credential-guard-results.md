The new guard's own "only expected files reference this enum member" scan

unrelated, pre-existing `"WRITE_SCOPE_EXCEEDS_TASK"` result code (see

## The real discovery: `verify_git_run` already does most of what a write guard needs

While building the isolation test above, `runtime/state/integrity.py`'s
pre-existing `WRITE_SCOPE_EXCEEDS_TASK` led to reading
`create_run_manifest` and `runtime/integrity/git_scope.py::verify_git_run`
in full. Confirmed by direct source read (not inferred): a run manifest
already stores a real `readable`/`writable`/`forbidden` scope contract
(`writable` defaults to the task's own `output_paths` when the caller
doesn't override it via `flow_start --write` / `maps run bind-session
--write`), and `verify_git_run` already does a real `git diff`-based
comparison of actual changed paths against that stored scope, returning
`out_of_scope` / `forbidden_changes`. It is real, already-shipped,
already-tested production code — just exposed only through
`runtime/integrity/cli.py run-verify-git`, advisory-on-request, never
consulted by any guard or dispatch flow. This is structurally identical to
the state the 6.16 row's own worktree-identity check was in before
`compare_worktree_identity`/`collect_git_worktree_identity` were wired into
`CanonicalRunGuard._require_bound_worktree` — same precedent, same shape of
fix.

**This was not attempted in this slice, on purpose.** Composing the new
`WriteScopeGuard` above changes zero live behavior (no firing site exists).
Wiring `verify_git_run`'s comparison into an already-fired event
(`BEFORE_RESUME` or `SESSION_STOPPING`, the same events `CanonicalRunGuard`
already runs on) would **not** be inert — every `recovery-tick
--enforce-canonical-run` pass already runs today would start comparing
each run's actual git changes against its (often-implicit,
defaulted-from-`output_paths`) writable scope on every resume/stop, which
could produce new denials on runs that previously passed. That is a real
behavior change to an already-partially-live enforcement path, not "add one
more guard" — squarely a bigger decision than this dispatch's bounded
scope. Flagging it here as the concrete next step rather than deciding to
build it unilaterally.
