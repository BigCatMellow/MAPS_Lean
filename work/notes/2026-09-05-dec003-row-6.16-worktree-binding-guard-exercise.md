## Finding 0 (blocking precondition, previously undiagnosed): `--require-worktree-binding` is a silent no-op without `--base-revision`

`maps flow start DEC003-616-1 --worker-id … --repo-root "$PWD" --lease-seconds 2400 --require-worktree-binding`
(no `--base-revision`) returned `FLOW_STARTED` **with `"worktree": null`** and
`"base_revision": null` — identical to PR #261's result that the checklist row
records as "not worktree-bound (`worktree: null`)".

Root cause, read directly in `runtime/state/integrity.py` (this clone,
`create_run_manifest`):

```python
worktree_identity: dict[str, str] | None = None
if base_revision is not None:                     # <-- whole block gated on base_revision
    try:
        worktree_identity = collect_git_worktree_identity(root)
    except RuntimeError:
        if require_worktree_binding:
            return MutationResult(False, "WORKTREE_BINDING_REQUIRED", …)
        worktree_identity = None
```

When `base_revision is None`, `collect_git_worktree_identity` is never called
and `require_worktree_binding` is never consulted — the flag cannot fail the
run and cannot bind an identity. The CLI help text
(`fail run creation unless repo-root has readable Git worktree identity`)
overstates what the flag does on its own.

**Workaround used (no runtime change):** pass `--base-revision <HEAD sha>`
alongside `--require-worktree-binding`. This is a real latent bug — flagged
for a follow-up task, same disposition as the two bugs in the `hila` note.

### Two extra repo-roots prepared to exercise the seam

genuinely different Git worktree identity than the one frozen at `flow start`.
A recovery-tick that runs in the same clone throughout can never trigger it —
the identity is identical. Two real, non-fabricated "different worktree"

## Pinning the `guard_code` — direct `CanonicalRunGuard` reproduction

The `recovery-tick` action dict flattens the guard veto to
`code: "HOOK_DENIED"` / `error: "Deterministic Hook denied the operation."` and
does not surface the guard's `guard_code` annotation. To pin exactly which
check denied, `CanonicalRunGuard.__call__` was reproduced against the
**identical** `TaskStore` (`.maps/state/maps.db`), the identical run manifest
`RUN-650b25de0e674a28bfd74859cc4efaed`, and an execution binding built from
that manifest, `operation="resume"` — the same objects the enforced
`recovery-tick` path constructs. `repo_root` was the only variable:

```
[same-clone]   repo_root=/tmp/dec003-616-103001
  actual identity == manifest.worktree (all 4 identity fields match)
  directive: DENY
  reason:  Session-bound operation requires explicit project, adapter, and session identity.
  guard_code: SESSION_REF_INCOMPLETE
  -> _require_bound_worktree returned None; the deny is the *downstream*
     _require_durable_session check reacting to the reproduction's synthetic
     session_ref, NOT the worktree seam. The worktree seam PASSES for the
     bound clone.

[linked-worktree]  repo_root=/tmp/dec003-616-linkwt
  actual identity: repo_root/git_dir/worktree_private_dir differ from manifest.worktree
  directive: DENY
  reason:  Run is bound to a different Git worktree than the one continuing it.
  guard_code: RUN_WORKTREE_MISMATCH

[non-git-dir]  repo_root=/tmp/dec003-616-nogit
  actual identity: <unreadable> RuntimeError('fatal: not a git repository …')
  directive: DENY
  reason:  Current Git worktree identity could not be read for a worktree-bound run.
  guard_code: RUN_WORKTREE_UNAVAILABLE
```

`__call__` evaluates `_require_live_claim` → `_require_current_run` →
`_require_bound_worktree` **before** `_require_durable_session`
(`runtime/policy/harness_guard.py`, `continuing` block precedes the
`session_bound` block). The `same-clone` reproduction reaching
`SESSION_REF_INCOMPLETE` proves `_require_live_claim` (lease live, task ACTIVE,
correct claimant), `_base_evidence` (revision current), `_require_current_run`
(not stale), and `_require_bound_worktree` (identity match) **all pass** for
the bound clone at tick-3 time. Therefore the tick 3a / 3b production denials —
same store, same manifest, same binding, same `now`, only `repo_root`
different — are necessarily `RUN_WORKTREE_MISMATCH` (3a) and
`RUN_WORKTREE_UNAVAILABLE` (3b), not an earlier check.

## What is and is not proven

**Proven:**

- `maps flow start --require-worktree-binding --base-revision <sha>` binds a
  concrete Git worktree identity into `run_manifest.worktree` (not `null`).
- On the real `recovery-tick --enforce-canonical-run` path, a stalled
  worktree-bound run whose resume is attempted from a **different Git worktree
  identity** is denied — `action: resume_denied`,
  `harness_resume: {attempted: true, code: "HOOK_DENIED"}`, incident parked
  `state: "denied"` with a canonical-denial counter, transient retry ladder
  untouched (matching the `hila` note's description of the `denied` state).
- The denial's `guard_code` is `RUN_WORKTREE_MISMATCH` for a linked worktree
  and `RUN_WORKTREE_UNAVAILABLE` for an unreadable worktree, confirmed by
  direct guard reproduction against the identical evidence.
- The worktree seam correctly **allows** (returns `None`) when the continuing
  worktree identity matches the bound one.
- This is `_require_bound_worktree`'s first exercise on a production code path
  (`build_canonical_harness_service` → `HarnessService.resume` →
  `HookEvent.BEFORE_RESUME` → `CanonicalRunGuard`), not a unit test.

**Not proven / caveats:**

- The tick 3a/3b `guard_code` is established by inference-from-source +
  direct reproduction, not by a `guard_code` field in the `recovery-tick`
  output itself (the CLI does not emit one). The inference is tight (see the
  ordering argument above) but it is an inference.
- A negative-control tick from the bound clone *through the full CLI while the
  lease was still live* was not achieved (the incident backoff window pushed
  the same-clone CLI tick past lease expiry, so it denied on `LEASE_EXPIRED`
  before reaching the worktree seam). The seam's allow-path is shown only by
  the direct reproduction (run at `03:32Z`, lease live).
- The "different worktree" was constructed by pointing `recovery-tick
  --repo-root` at a second checkout. This is a real, in-scope operation (the
  recovery supervisor genuinely takes `--repo-root`), and a linked `git
  worktree` is a genuine distinct worktree identity — nothing was fabricated —
  but in normal single-clone operation the supervisor and the bound run share
  a checkout and this seam would not fire. That is expected: it is a
  fail-closed guard against a specific misconfiguration/threat, not a
  common-path check.
