## 3. `BEFORE_DESTRUCTIVE_ACTION` hook-chain evidence

the supervisor does not persist the per-hook `HookInvocation` list. To capture
the hook chain the tick's `.stop()` executed, the call was **reconstructed**
immediately after the run using the **same composition root**
(`build_canonical_harness_service(task_reader, project_id="maps-lean",
repo_root=<clone>, hcom_dir="/home/home/.hcom")`) and the **same
lineage-resolution path** (`resolve_harness_binding(reader, incident,
session_name)`), against the **same task DBs and the same `recovery.json`
incident dicts**, with `HookRegistry.run` wrapped to record invocations. The
only difference from the in-tick call is the recording wrapper; the resulting
`OperationResult` matched the in-tick `harness_stop` codes exactly
(`HOOK_DENIED` for armed, `COMMAND_FAILED` for armed2), confirming fidelity.

## 4. Caveats / honest labelling (#303 style)

1. **The hook-chain trace in §3 is a reconstruction, not a byte capture of the
   tick's internal call.** It is faithful — same composition root, same binding
   resolver, same DB/incident inputs, and the reconstructed `OperationResult`
   codes match the in-tick `harness_stop` codes exactly — but the specific
   `guard_code` / `directive` / `reason` values are field-read from the
   reconstruction, not from the tick's output (which does not expose them).
   Confidence that the tick fired the identical chain: high (the only variable
   input, the binding, resolved to `binding_reason == ''` — a clean resolve —
   in both the tick and the reconstruction). Labelled ASSUMED→traced, not
   VERIFIED-from-tick.

2. **`guard_code="LEASE_EXPIRED"` on the resume denials is inferred, as in
   `CASE-378fb326…`.** The `harness_resume` dict carries `code: HOOK_DENIED`
   only; the `LEASE_EXPIRED` annotation is from `production.py`'s
   `build_canonical_harness_service` docstring + the fact that all three task
   leases (`--lease-seconds 90` / `60`) had expired > 40 min before tick 3. Not
   re-traced here.

3. **The armed (default-task) pass-3 outcome is a guard DENY, not a
   termination.** For an ordinary stalled task (`destructive_action: false` —
   the common case), the design-note call site fires `BEFORE_DESTRUCTIVE_ACTION`
   and the guard vetoes the stop with `ACTION_OUTSIDE_TASK_ENVELOPE`: the
   session is **not** terminated by recovery. Only a stalled task whose own
   policy envelope was authorized for destructive action (+ recorded operator
   reauthorization) — the armed2 lane — reaches the ALLOW path and an actual
   `adapter.stop()`. This is the design's intended fail-closed behaviour
   (§3c), but it means "`--terminate-denied-sessions` terminates a
   canonically-denied session" is true **only** for destructive-envelope tasks;
   for every other task the flag's observable effect is a recorded
   `harness_stop: {code: HOOK_DENIED}` and nothing else. Worth surfacing in the
   next 6.4 trajectory check — it may be the intended shape, or the call site
   may want the recovery *system's* authority rather than the stalled task's.

4. **armed2's `adapter.stop()` returned `COMMAND_FAILED`** because `viru` was
   already dead. The ALLOW-path evidence is that the chain reached the adapter,
   not that a live session was killed by it. Killing a still-live session via
   this path was out of scope (an incident only reaches the denial ceiling
   after ~45 min of the session being not-live in the hcom snapshot).

5. **`environment_evidence: null` / `resume_validation.reason: "no_spec_bound"`**
   on every action — no declared environment spec was bound to these throwaway
   runs. Not relevant to the destructive-action path.
