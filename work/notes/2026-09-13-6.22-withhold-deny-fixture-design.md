# Design: constructing a real task that fires `MemoryProvenanceGuard`'s non-vacuous branches

Roadmap 6.22 (`work/roadmaps/CAPABILITY_CHECKLIST.md` row 6.22). Follows the
PR #344/#346 first-exposure exercise (`work/notes/2026-09-12-6.22-before-send-first-exposure-exercise.md`):
that exercise's fixture task had *zero* recorded guidance/skills, so its
`memory_provenance` list was empty and `MemoryProvenanceGuard` fell through
to `GUARD_CODE_ALLOW_ADMITTED` having checked nothing — a vacuous pass. This
note designs the next fixture: a real task whose `memory_provenance` is
**non-empty**, so the guard's per-item admission loop actually runs.

Design-only. No `runtime/` code, tests, or `CAPABILITY_CHECKLIST.md` touched.

## (a) The guard's real branches, read from source

`runtime/policy/memory_provenance_guard.py::MemoryProvenanceGuard.__call__`,
per-entry loop (lines 162-209):

| Condition | Outcome |
|---|---|
| `admit_memory_evidence(trust_class, stale) == LOAD` | `continue` (no denial) |
| `== DENY` (unknown trust_class, or `UNTRUSTED_INPUT`/`QUARANTINED`) | denied — `{item}:{code}` |
| `== WITHHOLD` **and** `entry["embedded"] is True` | denied — `{item}:WITHHOLD_EMBEDDED` |
| `== WITHHOLD` **and** `entry["embedded"] is False` (explicit bool) | `continue` (referenced-only, no denial) |
| `== WITHHOLD` **and** `embedded` missing/non-bool | denied — `{item}:WITHHOLD_EMBEDDING_UNDECLARED` (fail-closed) |

If `denied` is non-empty after the loop → guard directive `DENY`
(`GUARD_CODE_DENIED`). If empty (including the case where every entry hit a
`continue`) → `ALLOW` (`GUARD_CODE_ALLOW_ADMITTED`) — the code the guard
already fired vacuously at #344.

`admit_memory_evidence()` (`runtime/policy/memory_trust_gate.py`) maps
`MemoryTrustClass` → `LOAD`/`WITHHOLD`/`DENY` via a fixed table: `LOAD` =
{`CANONICAL_POLICY`, `ACTIVE_INSTRUCTION`*, `APPROVED_SKILL`,
`REVIEWED_GUIDANCE`}; `WITHHOLD` = {`CANDIDATE_LESSON`, `CLAIM`,
`OBSERVATION`, `SUPERSEDED`, `RETIRED`}; `DENY` = {`UNTRUSTED_INPUT`,
`QUARANTINED`}. `stale=True` demotes `LOAD`→`WITHHOLD`, never promotes.
(*`ACTIVE_INSTRUCTION` is unreachable without a "proven active source"
prover that doesn't exist — floors to `WITHHOLD`.)

## Load-bearing finding: two of the four non-trivial branches are structurally unreachable through the real assembler as it exists today

This is the single most important thing a fresh reader needs before
building any fixture. Read directly against both real producers
(`runtime/context_builder.py` + `runtime/context_delivery.py`), not
inferred:

- **`WITHHOLD_EMBEDDED` (embedded=True + WITHHOLD) is unreachable.**
  `context_delivery.py::_guidance_lines_and_provenance` hard-codes
  `"embedded": True` only for items pulled from `plan["guidance"]`, and
  `context_builder.py::_route_lesson` only ever puts a `LOAD`-admitted item
  into the `guidance` bucket (`if admission is MemoryAdmission.LOAD:
  guidance.append(...)`, line 272-274) — every `WITHHOLD` item goes to
  `withheld_guidance` instead, which the renderer always marks
  `"embedded": False` (line 105). The renderer's own docstring says this in
  as many words: *"Under that rule a correctly-assembled payload is never
  denied by the BEFORE_SEND memory-provenance guard — that guard's deny
  path exists to catch an assembler bug or a future looser renderer."*
  Skills go through the same shape: `_skill_lines_and_provenance` sets
  `embedded = isinstance(body, str) and bool(body.strip())`, and a Skill
  body is only ever attached when `context_builder.py`'s own skill-selection
  loop already resolved the Skill to `LOAD` — a `WITHHOLD`-classed Skill
  never gets a `body`, so `embedded` is always `False` for it too.

- **`WITHHOLD_EMBEDDING_UNDECLARED` (embedded missing/non-bool) is
  unreachable.** Every provenance entry either producer emits always sets
  `"embedded"` to an explicit `bool` (`True`/`False` in
  `context_delivery.py` lines 81/105/146). There is no code path in the real
  renderer that omits the key or sets a non-bool value.

- **The per-item `DENY` branch is unreachable — and so is the guard-level
  `GUARD_CODE_DENIED` outcome.** `context_builder.py` filters `DENY`-classed
  items out *before* they ever reach a plan bucket: `_route_lesson` returns
  immediately on `admission is MemoryAdmission.DENY` (line 270-271, no
  append to either list — the item gets **no provenance entry at all**), and
  the Skill-selection loop does the identical `continue` on `DENY` (line
  550-551) before building the `item` dict. A `DENY`-classed item never
  reaches `render_context_send_payload` in the first place, so it can never
  appear in `memory_provenance`, so the guard can never see it. Separately:
  no real producer in this codebase currently emits `UNTRUSTED_INPUT` or
  `QUARANTINED` for a lesson (`operational_learning_trust_class` only maps
  `CANDIDATE`/`ACTIVE`/`RETIRED`, none of which is `DENY`-classed) — the only
  live path to a `DENY`-classed trust class is a Skill whose
  `SkillLifecycleState` is `QUARANTINED`, and that Skill is filtered out
  before it ever becomes a provenance entry, per the paragraph above.

**Consequence:** reaching a real `DENY` guard outcome, or exercising either
of the two unreachable per-item branches, is not possible by constructing
*any* real task through the existing legitimate pipeline — the producers
already enforce, upstream of the guard, exactly the invariant the guard
exists to double-check. Doing it anyway requires either (i) a genuine
producer bug (not something to induce on purpose), or (ii) deliberately
constructing an adversarial payload that violates the renderer's own
invariant and driving it through the real `send()` codepath — which is a
different *kind* of exercise from a naturally-occurring task, and is
addressed separately in (c) below rather than folded into "the next
fixture," because it is materially more invasive than #305/#344's
precedent and needs its own explicit sign-off.

## (b) A concrete, constructible real task that exercises the reachable `WITHHOLD` branch

Goal: get one real, non-vacuous pass through the `WITHHOLD` + `embedded is
False` → `continue` line (currently exercised zero times — #344's list was
empty, not merely all-`continue`). This uses only the existing
operator-promotion mechanism; no schema/store change.

1. **Record a CANDIDATE lesson** via
   `TaskStore.record_operational_lesson_candidate()` with a real `claim`,
   `source_kind`/`source_refs` pointing at this note or a real prior
   incident, and an `applicability` block that *matches* the target task
   below (same `project_id`/`task_type`/`risk`/output path prefix — see
   `runtime.operational_learning._match_applicability`).
2. **Promote it** via `TaskStore.promote_operational_lesson()` (operator-only,
   real `decision_ref`) with `review_at` set to a timestamp already in the
   past relative to when step 4 runs. (`starts_at` in the past, no
   `expires_at`, so the only withhold reason that fires is `REVIEW_DUE` —
   deliberately choosing the reason that requires no timing race, unlike
   `NOT_APPLICABLE`/`APPLICABILITY_UNKNOWN` which depend on matcher
   internals.)
3. **Create a real task** (`maps task create` or equivalent) whose
   `project_id`/`task_type`/`risk`/`output_paths` match the lesson's
   applicability from step 1 — so that, absent the `REVIEW_DUE` demotion,
   this lesson would otherwise have been `LOAD`-admitted. This is what makes
   the exercise genuine: the lesson is a real, relevant, promoted piece of
   guidance that the trust gate is *actively* withholding, not an inert
   record that would never have been offered anyway.
4. **Run the real production call site**, exactly as #344 did:
   `maps run send-context --deliver-context` against a genuinely live hcom
   session, with `from_name` and the task from step 3.
5. **Observe and record**, independently reviewed exactly as #344/#346 were:
   - The rendered `send()` payload's `memory_provenance` now contains
     **one entry**: `{"item_id": "<lesson_id>", "trust_class":
     "REVIEWED_GUIDANCE", "embedded": false, "stale": true, ...}` (an
     `ACTIVE` lesson maps to `REVIEWED_GUIDANCE` per `runtime/trust.py`;
     `stale_trust_metadata` is set by
     `context_builder._withheld_lesson_with_trust_class` for every
     already-withheld lesson).
   - `admit_memory_evidence("REVIEWED_GUIDANCE", stale=True, ...)` returns
     `WITHHOLD` (stale demotes the otherwise-`LOAD` class) —
     `context_builder._route_lesson`'s `floor_withheld=True` path would have
     forced `WITHHOLD` regardless, so this is doubly fail-closed, worth
     confirming both ways in the exercise's own note.
   - `MemoryProvenanceGuard.__call__` now runs its per-entry loop with **one
     real iteration** instead of zero: `decision.admission is WITHHOLD`,
     `entry["embedded"] is False` → the `continue` branch fires — the first
     real, non-vacuous execution of that line.
   - The guard's final directive is still `ALLOW`
     (`GUARD_CODE_ALLOW_ADMITTED`) — **this exercise does not produce a
     `DENY`, and the checklist row's evidence text must say so explicitly,
     not imply otherwise.** What it proves, that #344 didn't: the guard's
     admission re-derivation and its embedded/referenced-only branch both
     ran for real against a real withheld item, not against an empty list.
   - Message body: confirm the rendered text contains the withheld
     reference line (`"- [<lesson_id>] withheld (REVIEW_DUE); pursue
     explicitly to load"`) and **not** the lesson's `claim` text — the
     concrete, human-checkable proof that the withheld content stayed out of
     the embedded body.

This is the smallest legitimate next step, same rigor as #305/#344: a real
CLI verb, a real live session, real independent review, no mock, no
log-only simulation.

## (c) What it would take to see a real `DENY` — named, not attempted here

Per the load-bearing finding above, no organically-constructed task can
produce a guard `DENY` today. The only way to exercise it for real (through
the actual `HarnessService.send()` → `BEFORE_SEND` → guard codepath, not a
unit-test double) is to hand-assemble a payload that violates
`render_context_send_payload`'s own invariant — e.g. call `HarnessService.send()`
directly with a payload whose `memory_provenance` entry has
`{"trust_class": "CANDIDATE_LESSON", "embedded": true}`, bypassing the
renderer. This is a legitimate **defense-in-depth / adversarial** exercise
— proving the guard still catches a bad payload even though the current
renderer is never supposed to produce one — but it is a different exercise
in kind from (b): it does not arise from a real task's real data, it is a
deliberately constructed adversarial input. Naming it here per this task's
stop condition, **not attempting it**: whether to run it, and how to
characterize its evidence (it proves the *guard*, not the *pipeline*, is
correct) is a decision for the operator/coordinator, not something this
design note pre-authorizes.

## (d) Explicit non-goals

- Does not modify `MemoryProvenanceGuard`, `admit_memory_evidence`,
  `context_builder.py`, or `context_delivery.py`.
- Does not add a schema/store change, a new `MemoryTrustClass`, or a new
  producer of `UNTRUSTED_INPUT`/`QUARANTINED`.
- Does not attempt to construct a real `DENY` outcome — (c) names why and
  defers the decision.
- Does not flip `CAPABILITY_CHECKLIST.md` row 6.22 to `DONE` — even after
  (b)'s exercise runs, the row's real remaining gap (a real `DENY`/embedded
  `WITHHOLD` firing) stays open per (c).
- Does not touch `tests/` — the fixture construction in (b) is a live
  exercise (task + lesson + real CLI call), not a unit test; if a follow-up
  wants a regression test pinning the reachability finding in (a), that is
  a separate, explicitly-scoped task.

## Verification (this note alone should be enough to build (b))

A fresh reader can, from this note alone: (1) call
`record_operational_lesson_candidate()` then `promote_operational_lesson()`
with a `review_at` in the past, (2) create a matching real task, (3) run
`maps run send-context --deliver-context` against it, (4) grep the rendered
payload for a non-empty `memory_provenance` with `trust_class:
REVIEWED_GUIDANCE`, `embedded: false`, and (5) confirm via
`hcom events --agent <recipient>` that the message was actually delivered —
the same delivery-proof shape #344 used. Evidence that would fail this: an
empty `memory_provenance` (means applicability/timing didn't line up), or a
`LOAD`-admitted entry (means the `REVIEW_DUE`/staleness demotion didn't
fire — check `review_at` is actually in the past relative to the run).
