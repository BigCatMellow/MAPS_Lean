## Verdict: **PARK**

There is **no production consumer** that needs to verify a Skill resource in
isolation. `load_skill_resource` (slice 2) already returns
whole-directory-hash-verified bytes for the one file a caller asks for, and it
has **zero production callers** itself. Adding per-resource digests now is
speculative infrastructure for a consumer that does not exist — rule 8
(smallest change) and rule 13 (bounded first, machinery on repeated evidence)
both say defer.

**But the design is fully specified below (§3)** so the impl is a one-shot
dispatch the moment a real consumer appears — and §4 names the fork that would
*change* the verdict (a partial-read verification strategy, which is a larger
design than "add a field").

## 2. The four dispatch questions

### Q1 — Is per-resource `sha256` needed, and by whom?

**Not today.** Trace the would-be consumers:

| Candidate consumer | Exists? | Does it need per-resource `sha256`? |
|---|---|---|
| `load_skill_resource` callers | **No** (`/usr/bin/grep -rn "load_skill_resource" runtime/ --include=*.py` → only the `runtime/skills/__init__.py` re-export + doc mentions in `context_builder.py` / `flow_start.py`) | It already whole-dir-verifies before returning bytes — a per-resource digest is redundant on that path. |
| A downstream reader of `plan["skills"][i]["execution_resources"]` | **No** (nothing reads the context plan's skill-resource manifest; the manifest is attached but inert) | *Would* want it — to verify a resource it pulls out-of-band against a value from the plan, without re-invoking `load_skill_resource`. |
| A re-discovery / review workflow that wants to know *which* resource drifted | **No** (a content change raises `SkillChangedError` for the whole Skill; nothing localizes it) | *Would* want it — "`scripts/x.sh` changed, `references/y.md` unchanged". |
| A partial-verification fast path (`load_skill_resource` that reads only the one file) | **No** — and it would be a **new verification strategy** (§4), not this slice | Needs it as the anchor to compare a single-file read against. |

Every real use is hypothetical. `load_skill_resource`'s existing whole-dir
verification is sufficient for every path that exists. **No requirement → PARK.**

### Q2 — If it *were* scoped: exact shape

1. **Where computed** — `runtime/skills/format.py::_descriptor_for_root`. Unlike
   `_resource_sizes` (which only `stat()`s), a digest needs the bytes. The bytes
   for `content_sha256` are **already read** in `_directory_hash` /
   `_regular_files` → `path.read_bytes()`. Add `_resource_hashes(skill_root,
   resources)` computing `hashlib.sha256(path.read_bytes()).hexdigest()` per
   declared resource — or, to avoid a second read pass, fold per-file digests
   into the single `_directory_hash` walk and return them alongside the whole-dir
   digest (a small refactor of `_directory_hash` / `_hash_snapshot`). `load_skill`
   rebuilds from `_verified_snapshot`'s already-read snapshot (zero extra I/O
   there).
2. **Field** — `SkillDescriptor.resource_hashes: tuple[tuple[str, str], ...] = ()`
   — `(relative_path, sha256_hex)`, **mirroring `resource_sizes` exactly**
   (same shape, same ordering = `resource_paths` order, same `= ()` default).
   Add it to the `SkillChangedError` identity check in `load_skill` (the line
   next to `or current.resource_sizes != descriptor.resource_sizes`) and in
   `assess_skill` if that has a parallel check.
3. **Manifest** — `_execution_resource_manifest` adds `"sha256"` to each entry:
   `sizes.get(path)` → also `hashes.get(path)` from
   `dict(descriptor.resource_hashes)`; `None` when unrecorded (never silently
   dropped, matching the `size_bytes` `None` convention).
4. **Does it change `load_skill_resource`'s verification?** **No** — the minimal
   slice keeps whole-dir `_verified_snapshot` verification (strongest, and free
   since it must read everything to recompute `content_sha256` anyway). A
   per-resource fast path is §4, explicitly out of this slice.

Net: it is genuinely "add one field parallel to `resource_sizes` + surface it
in the manifest" — *iff* per-resource verification is not also in scope.

### Q3 — Operator decision?

**None.** A per-resource digest that is only *computed, recorded, and exposed in
the manifest* is not an authority surface. The 6.11 guardrail
(`work/tasks/context-budget-classification-wave12.md`) is specifically about a
field that **drives load/fetch behaviour** ("auto-loading MUST_LOAD items,
auto-fetching SHOULD_LOAD items … requires operator approval"). `resource_hashes`
would drive nothing — like `resource_sizes`, it rides the trust gate's existing
`LOAD` decision and is descriptive metadata. Confirmed against the 6.11 row and
the wave12 escalation clause: **not an operator decision.**

(If a future slice made `load_skill_resource` *decide* whether to read the whole
dir vs. one file based on `resource_hashes` — §4 — that is still not an operator
decision either, it is a verification-strategy design choice; but it is a bigger
change than this slice.)

### Q4 — STOP-condition check

- *The only real value requires a new mechanism, not a field?* — **This is the
  fork (§4).** If slice 3's actual goal turns out to be the **partial-read
  efficiency** ("verify one resource without reading the whole directory"), that
  is a new verification strategy in `load_skill_resource` (read one file, hash
  it, compare to `resource_hashes[path]`, skip `_verified_snapshot`) — larger
  than "add a field", with its own correctness surface (what if a *sibling*
  file changed — the whole-dir `content_sha256` no longer matches, but the one
  file is fine; is that acceptable?). **Flagged to @soda.** The field-only slice
  (§Q2) does not trip this; the efficiency slice does.
- *Needs infrastructure beyond format.py + context_builder.py?* — **No** (for the
  field-only slice).
- *An operator-only decision blocks it?* — **No** (§Q3).

No STOP condition on the **field-only** slice. The **efficiency** interpretation
is a separate, larger design — do not conflate.

## 4. The fork — partial-resource verification (a *different*, larger slice)

If the real motivation for per-resource `sha256` is **not** "expose it in the
manifest" but "**verify one resource without reading the whole Skill
directory**" (an efficiency win for a Skill with many large `references/` /
`assets/` files when a consumer wants one), then slice 3 is **not** "add a
field" — it is:

- `load_skill_resource(descriptor, relative_path, *, verify="directory" |
  "resource")` (or a new function) that, for `verify="resource"`, reads only
  `<root>/<relative_path>`, hashes it, compares to
  `dict(descriptor.resource_hashes)[relative_path]`, and returns — **skipping
  `_verified_snapshot`**;
- a correctness decision: `verify="resource"` accepts a Skill directory where a
  *sibling* file changed (whole-dir `content_sha256` no longer matches, but the
  requested file is byte-identical to discovery). Is that a feature (localized
  trust) or a hole (the Skill as a whole is no longer the discovered artifact)?
- a caller-contract decision: does the default stay `"directory"` (safe) and
  `"resource"` is opt-in for a caller that has accepted the trade-off?

This is a real design with an actual decision in it, and it is worth a slice —
but it is **larger than the §3 field-only slice** and should be scoped
separately if that is what's wanted. **@soda: confirm which interpretation
slice 3 is meant to be** — the field-only refinement (PARK per §Verdict, spec
ready in §3) or the partial-verification capability (its own scoping pass).
