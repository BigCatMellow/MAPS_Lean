# Design: wiring `verify_git_run`'s scope-check half onto an already-fired guard event

Roadmap 6.4 (`work/roadmaps/CAPABILITY_CHECKLIST.md` row 6.4). Dispatched by
coordinator `venu` as the follow-up to
`work/notes/2026-09-15-6.4-write-credential-guard-design.md` §4a's finding
(PR #360): `runtime/integrity/git_scope.py::verify_git_run` already does
real, post-hoc write-scope verification, currently advisory-only, and the
6.16 worktree-identity check was in the same state before being wired into
`CanonicalRunGuard`. Brief: scope exactly what wiring the *scope-check* half
of `verify_git_run` onto an already-fired enforced-pass event would change
in live `recovery-tick` behavior, mirroring that 6.16 precedent; name the
first-exposure exercise, do not build it; stop and flag rather than decide
unilaterally if scoping reveals a live-semantics change needing sign-off
before even this note.

**Design-only. No `runtime/` changes. This note's own conclusion is a stop,
per the dispatch's own stop condition — read to the end before treating any
earlier section as a settled recommendation.**

## 1. The precedent, read from its own origin note, not assumed

The 6.16 worktree-identity wiring was scoped in
`work/notes/2026-08-26-worktree-binding-enforcement-seam-design.md`. That
note's own "Why this was not wired directly in this pass" section
(hazard 1) says, verbatim:

> `verify_git_run()` is too broad for this seam. Beyond comparing worktree
> identity it calls `collect_git_changes()` ... and then
> `store.verify_run_changes()`. Calling it from `BEFORE_SEND` would run two
> Git subprocesses on every message and would **also deny on out-of-scope
> changed paths — a much larger authority expansion than worktree binding**,
> and one E6's checklist row explicitly disclaims.

This is the load-bearing fact for this note: **the scope-check half of
`verify_git_run` was not merely "not gotten to yet" when the worktree half
was wired — it was explicitly identified and deliberately excluded as a
materially larger authority expansion, three weeks before this dispatch.**
This note is not the first pass at this question; it is picking up a
decision the original design already made, and re-examining it with fresh
evidence (§2) rather than re-litigating it from nothing.

`work/tasks/run-worktree-binding.md`'s "Stop / escalate" section (the E6
task's own authority boundary, still in force) names exactly this class of
change:

> Stop rather than guess if: ... failure semantics that would block
> legacy/unbound runs automatically; ... verifier semantics would change
> task/review authority. Escalate to: operator or a follow-up design task.

## 2. Why worktree binding was safe to wire directly, and scope is not — the structural asymmetry

Re-verified against current source (`runtime/state/integrity.py::create_run_manifest`,
`runtime/policy/harness_guard.py::CanonicalRunGuard._require_bound_worktree`),
not inferred:

**Worktree identity has a genuine, persisted "not opted in" state.**
`create_run_manifest`'s `worktree_identity` stays `None` unless the caller
passes `base_revision` (and `require_worktree_binding` additionally
requires it or the manifest write fails loudly —
`WORKTREE_BINDING_REQUIRES_BASE_REVISION`, from the #303 exercise's own
named residual bug). The guard's `_require_bound_worktree` reads
`manifest.get("worktree")`, and when it is not a mapping, returns `None`
(allow) immediately — a clean, safe no-op for every run that did not
explicitly ask for worktree binding. That is what made composing it
directly into the always-registered `CanonicalRunGuard` safe: only
runs that opted in were ever affected.

**Readable/writable/forbidden scope has no such state.** Re-read
`create_run_manifest`'s signature and body directly:

```python
def create_run_manifest(
    self, task_id, worker_id, *, repo_root, created_by,
    session_id=None, context_paths=(),
    readable_paths=(".",),
    writable_paths=None,
    forbidden_paths=(),
    ...
):
    ...
    readable = self._normalize_scopes(readable_paths, root)      # always runs
    forbidden = self._normalize_scopes(forbidden_paths, root)    # always runs
    ...
    normalized_parent = self._normalize_scopes(parent_outputs, root)
    writable = self._normalize_scopes(
        writable_paths if writable_paths is not None else parent_outputs,
        root,
    )                                                              # always runs
```

Every run gets a computed, persisted `readable`/`writable`/`forbidden`
triple, unconditionally — `readable` defaults to `(".",)` (the whole repo),
`forbidden` defaults to `()` (empty), `writable` defaults to the task's own
`output_paths` when the caller doesn't pass `writable_paths` explicitly.
**Nothing on the persisted manifest distinguishes "the caller explicitly
declared this scope" from "the caller passed nothing and got the default."**
Unlike `worktree`, there is no `None`/absent case for a new guard to
no-op on. A guard mirroring `_require_bound_worktree`'s shape
(`if not populated: return None`) cannot be written for scope, because
scope is never unpopulated.

## 3. Consequence: the blast radius is not bounded the way the worktree wiring's was

Of the three scope fields, two are practically inert under their defaults:
`readable` defaulting to the whole repo and `forbidden` defaulting to empty
will essentially never trip `verify_git_run`'s `out_of_scope`/
`forbidden_changes` checks on their own. **`writable` is not inert.** Its
default is the task's own `output_paths` — real, narrow, per-task data —
and `verify_git_run`'s `collect_git_changes()` diffs the *entire* working
tree (`git diff --name-status` against `base_revision`, plus
`git ls-files --others --exclude-standard` for untracked files) against
that scope. Composing a guard that consults this on an already-fired event
(`BEFORE_RESUME` or `SESSION_STOPPING`, mirroring where `CanonicalRunGuard`
already runs) means: from the moment it is composed, **every** run passing
through an enforced `recovery-tick --enforce-canonical-run` pass — not just
runs that opted in — has its actual git-changed paths compared against its
(usually implicitly-defaulted) `output_paths`, and denied continuation on
any path outside that scope.

Whether that is a small or large practical risk turns on one empirical
question this note could not answer with confidence: **how narrowly do real
tasks declare `output_paths` relative to the paths they legitimately touch?**
This session's own just-merged work (PR #360) is one concrete data point
against optimism: it touched `runtime/policy/`, `tests/`, `work/notes/`,
and `work/roadmaps/CAPABILITY_CHECKLIST.md` in one task — four different
top-level areas — which is an entirely ordinary shape for real MAPS_Lean
work (code + test + design note + checklist update), not an edge case.
Checked for real production data to ground this further: the coordinator
checkout's local `.maps/state/maps.db`
(`~/Projects/MAPS_Lean/.maps/state/maps.db`, read-only query) has only two
`task_output_paths` rows (`LBW-EXERCISE-1 -> work/notes`,
`TASK-0001 -> tmp/env-exercise-6-24-out.md`) — stale leftover fixture state
from old exercises, not the live fleet's actual task volume, so **this is
an explicit unknown, not a resolved one** (rule 15 — stating it rather than
guessing). Whatever the live fleet's actual `.maps/` data shows, this note
does not have access to it and does not assume an answer either way.

## 4. The fork this creates — named, neither branch chosen here

**(A) Enforce against the implicit default, now.** Wire `verify_git_run`'s
comparison into `BEFORE_RESUME`/`SESSION_STOPPING` unconditionally, reusing
`readable`/`writable`/`forbidden` exactly as `create_run_manifest` already
computes and stores them. Cheapest to build (no schema change — the guard
is a straightforward mirror of `_require_bound_worktree`'s shape, minus the
"return None if unpopulated" escape hatch, since none exists). Risk: every
enforced pass immediately starts denying continuation for any run whose
actual changes drifted outside its (possibly-never-consciously-declared)
`output_paths` — including, plausibly, a large fraction of ordinary
multi-area work per §3's data point. This is precisely "failure semantics
that would block legacy/unbound runs automatically," the exact case
`work/tasks/run-worktree-binding.md`'s own escalation trigger names,
except here there is no "unbound" case to exempt — it would be closer to
"failure semantics that would block *every* run automatically" until each
task's `output_paths` is deliberately widened to match its real footprint.

**(B) Add a genuine opt-in signal first, mirroring `require_worktree_binding`.**
Give `create_run_manifest` a new explicit flag (e.g.
`require_write_scope_binding`) that, when set, records on the manifest that
the caller *consciously* declared scope (not merely defaulted) — the same
shape `require_worktree_binding` + `base_revision` already establishes for
worktree identity, including the same "flag without its companion is a
silent no-op, fail loudly" discipline #303's own named residual bug forced
onto the worktree path (`WORKTREE_BINDING_REQUIRES_BASE_REVISION`). A guard
would then no-op on every run that did not opt in, exactly like
`_require_bound_worktree` does today. This is safe by the same construction
that made the worktree wiring safe — but it is **not** "just wire an
existing function": it is a schema/behavior addition to
`create_run_manifest` (a new column or flag, new CLI surface on
`flow_start`/`run-create`, and a decision about whether existing runs with
only-defaulted scope are ever retroactively covered). That is real,
separately-scoped work, not a sub-step folded into "wire `verify_git_run`."

## 5. Stop, per this dispatch's own stop condition

Scoping this did reveal that (A) is not a safe drop-in mirror of the
worktree precedent the way the dispatch's framing assumed, and picking
between (A) and (B) is itself a live-enforced-pass semantics decision —
exactly the class of thing `work/tasks/run-worktree-binding.md`'s
"Decision authority" section reserves to the owner/operator ("failure
semantics that would block legacy/unbound runs automatically" is an
escalate-item, not something an implementer decides). Per this dispatch's
own instruction ("if scoping reveals it changes live enforced-pass
semantics in a way that needs explicit sign-off before even a design note,
say so and stop rather than deciding unilaterally"): **stopping here.**
This note names the fork and the evidence behind each side; it
deliberately does not pick (A) or (B), does not scope a concrete
first-exposure exercise for either (the exercise looks completely
different depending on which branch is chosen), and does not touch
`runtime/`. The decision needed next is which of (A)/(B) — or "neither, not
now" — the coordinator/operator wants, informed by real `output_paths`
granularity data from the live fleet if available (§3's unknown).

- Does not pick between (A)/(B) in §4.
