## 1. The actual failure mode in each category (real EXP-B cases)

Current mechanism (`context_builder.py:419-431`): `signals =
_skill_task_signal_tokens(task)` (tokens ≥3 chars from `task_type` +
`project_id` + output-path stems, regex `[a-z0-9]+`); `skill_tokens =
_text_tokens(name) | _text_tokens(description)`; `matched = signals &
skill_tokens`; **any** non-empty `matched` → selected. No weighting, no
threshold, no normalisation, no tie-break.

### VOCABULARY_SHIFT — zero lexical intersection (→ ABSTAIN, wrong)

| Case | Task signal tokens (abridged) | Target Skill's concept words | Overlap |
|---|---|---|---|
| V01 | credential, renewal, cycle, material, refresh, pinned, edge, proxy, handshake | rotation, **credentials**, signing, keys, bearer, tokens, tls, certificates | **∅** (`credential` ≠ `credentials` — morphology) |
| V02 | sitewide, brownout, checkout, degradation, blast, radius, notes | outage, triage, rollback, incident, timeline, disruption, impact | **∅** (pure synonymy) |
| V03 | endpoint, signature, comparison, billing, gateway, openapi, payload, shape, audit | http, interface, compatibility, versioning, deprecation, breaking, contract | **∅** (pure synonymy) |
| V04 | readiness, surge, soak, signup, headroom, spike, tolerance, writeup | performance, capacity, workload, ramp, throughput, traffic, targets | **∅** (pure synonymy) |

V01 is a **morphological** miss (`credential`/`credentials`). V02–V04 are
**semantic** misses — the task never contains a literal Skill concept word;
routing requires knowing `brownout ≈ outage`, `soak ≈ load test`,
`payload shape ≈ contract`. That is domain query expansion.

### HARD_NEGATIVE — one accidental generic token fires (→ SELECT, wrong)

| Case | Accidental overlap | Skill it wrongly hits | Task actually is |
|---|---|---|---|
| H01 | `load`, `test` (2) | load-test-planning | unit-test fixture loading |
| H02 | `rotation` (1) | secrets-rotation | logrotate / disk cleanup |
| H03 | `api` (1) | api-contract-review | rate-limit tuning |
| H04 | `release`, `launch` (2) | changelog-authoring, load-test-planning | marketing launch event |

Failure mode: **no relevance bar.** `rotation` / `api` / `release` / `load`
are low-information tokens — they appear as incidental words, not as the task's
subject. A single such overlap is treated as a match. H01/H04 even overlap on
2 tokens, so a bare "≥2 tokens" rule would not fix them — the fix has to weight
by how *distinctive* the token is and/or how much of the task the match covers.

### AMBIGUOUS — no confidence signal, flat SELECT list (→ SELECT, non-exact)

| Case | Shared token | Skills it hits | Correct outcome |
|---|---|---|---|
| A01 | `version` (+ `library`, `bump`, `notes`) | api-contract-review, changelog-authoring, dependency-upgrade-review | AMBIGUOUS (3-way) |
| A02 | `rollback` (+ `runbook`, `service`) | data-migration-runbook, incident-response-playbook | AMBIGUOUS (2-way) |

`_select_skills` returns `(list, tally)` — there is **no channel** to say "these
are candidates I cannot disambiguate." The eval adapter
(`test_exp_b_skill_routing.py::_run_predictions`) maps `names → SELECT if names
else ABSTAIN`, so a multi-Skill result is indistinguishable from MULTI_SKILL.
Note: surfacing 2–3 candidate Skills as *evidence* is not itself harmful (it is
what MULTI_SKILL wants) — the "miss" is a labelling gap, not a safety gap.

## 2. Smallest change per failure mode, within "explicit-first, no semantic retrieval"

### HARD_NEGATIVE → match-strength score + minimum threshold — **RECOMMENDED, SCOPE**

Replace `if not matched: continue` with a score gate. The score is computed
**from the candidate catalog only** (no index, no model, no external data):

- **Token distinctiveness.** For each matched token, `1 / (# candidate Skills
  whose name|description contains it)` — a token in one Skill's text is worth
  1.0; a token shared by 3 Skills is worth ~0.33. (Optionally floor common
  English function words at 0 via the *existing* need for a small stopword set —
  see below.)
- **Coverage.** Fraction of the task's signal tokens that matched, and/or
  fraction of the Skill's own concept tokens that matched. H01's task has ~8
  signal tokens, 2 matched → low coverage; a DIRECT case matches most of them.
- **Gate:** admit only if aggregate score ≥ a floor **and** the match includes
  ≥1 distinctive (≈ Skill-specific) token. The floor is a **reviewer judgment**
  chosen from the mechanism ("a lone generic token must not select"), not
  fitted to an EXP-B number.

Regression risk to the 1.00 categories: **low.**
- DIRECT (D01–D05): matches are multi-token and land on Skill-specific concept
  words (`schema`/`backfill`/`cutover`, `throughput`/`capacity`) — high score.
- PARAPHRASE (P01–P04): P01/P03 are the thin ones (they lean partly on a
  name-shared token). **These are the cases to watch** — the impl must confirm
  P01 (`migration`+`schema`+`backfill`+`cutover`) and P03
  (`dependency`+`transitive`+`advisory`+`lockfile`) still clear the floor.
- MULTI_SKILL (M01–M02): each of the two Skills must independently clear the
  floor — verify.
- NO_SKILL (N01–N04): already ∅ overlap — unaffected.
EXP-B re-run is the mandatory check.

### AMBIGUOUS → margin rule on the same score — **SCOPE (rider on the above)**

Once every candidate has a score: if the top candidate's score and the 2nd
(3rd) candidate's score are within a **margin** and ≥2 candidates clear the
floor, `_select_skills` attaches an ambiguity marker (e.g.
`plan["skills_ambiguous"] = True` or per-item `"ambiguous_group": [...]`), and
the eval adapter maps that to `SkillSelectionOutcome.AMBIGUOUS`. Plan-shape
addition is additive (no existing consumer breaks). The margin is a reviewer
judgment. Distinguishing AMBIGUOUS from MULTI_SKILL: MULTI_SKILL cases have
*independently strong, non-overlapping-reason* matches; AMBIGUOUS cases have
*near-equal scores driven by the same shared token* — the margin rule captures
exactly that.

Regression risk: **low** — MULTI_SKILL matches are strong and reason-distinct,
so they should fall outside the margin; verify M01/M02 stay `SELECT` (both).

### VOCABULARY_SHIFT → **split**

- **Light lemmatiser (plural/tense normalisation): SCOPE.** Normalise both
  sides with a tiny deterministic rule set (trailing `s`/`es`, `ing`, `ed`;
  ~10 lines, no dependency). Closes **V01** (`credential`→`credentials` stem
  `credential`). Does **not** touch V02–V04. Regression check: plural collapse
  can create matches (`keys`→`key`, `notes`→`note`) — EXP-B re-run required,
  especially A01 (`notes`) and H-cases.
- **Curated synonym / query-expansion map for V02–V04: PARK — §6.33.** See §5.

### The stopword set (enabling dependency for HARD_NEGATIVE scoring)

The distinctiveness score is cleanest with a small curated stopword list
(generic verbs/nouns: `review`, `check`, `plan`, `service`, `notes`, `docs`,
`test`, …). This is **explicit-first** (a hand-authored constant, like
`_MIN_TOKEN_LEN`), not retrieval. Its contents are reviewer-curated. ~20–40
entries.

## 5. STOP-condition check (per the trajectory playbook)

**Is the real increment blocked on a retrieval mechanism?** — **Partly.**

- HARD_NEGATIVE: **not blocked.** Distinctiveness + coverage scoring is a pure
  function of the candidate catalog. Explicit-first. SCOPE.
- AMBIGUOUS: **not blocked.** A margin rule on the same score + an additive plan
  field. SCOPE.
- VOCABULARY_SHIFT (V02–V04): **BLOCKED on query expansion / semantic
  similarity** — roadmap **§6.33** ("Context Builder stays explicit-first";
  promotion-gated on "a frozen evaluation … must demonstrate meaningful
  improvement over explicit/baseline"). Chasing it now with an ad-hoc synonym
  map would (i) pre-empt §6.33's gate, (ii) risk HARD_NEGATIVE regressions
  (adding `release ≈ changelog` degrades H04), (iii) be unbounded reviewer
  curation. **PARK.** Only the plural/tense lemma normalisation (V01) is taken.

**Consequence for 6.9/S6 DONE:** the impl PR closes HARD_NEGATIVE + AMBIGUOUS
and 1/4 VOCABULARY_SHIFT. The remaining 3/4 synonym gap is resolved by **path
(b)** — a §17.3 reviewer/operator ruling that the narrowed behaviour is
acceptable for promotion (recommended: yes, per §3) — **or** it waits on §6.33.
6.9/S6 does **not** reach DONE purely by this impl; it reaches
"HARD_NEGATIVE + AMBIGUOUS closed, one §17.3 ruling away from DONE."
