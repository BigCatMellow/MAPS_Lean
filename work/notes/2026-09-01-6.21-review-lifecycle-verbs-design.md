## 1. Re-verified state

### 1a. What exists

- `runtime/flow_review.py::flow_review_start` — composes review preflight +
  claim (+ optional immutable subject bind), stops before verdict. Payload
  `next_step.state = "STOPPED_BEFORE_REVIEW_VERDICT"`.
- `runtime/state/review.py::record_review(task_id, reviewer_id, verdict,
  summary, *, rederived_artifact_refs=None, now=None)` — the **only** operation
  that closes an open review row. Enforces: reviewer owns the open review
  (`NOT_REVIEW_OWNER`); task still `READY_FOR_REVIEW` (`NOT_REVIEWABLE`);
  submission present; independence still holds (`CONTINUITY_REVIEW_FORBIDDEN`);
  criterion verification complete (`CRITERION_VERIFICATION_INCOMPLETE`); and the
  review-binding approval hook `_validate_review_approval_conn`
  (`runtime/state/review_binding.py:496`). Verdict → status:
  `APPROVED→DONE`, `CHANGES_REQUESTED→CHANGES_REQUESTED`, `BLOCKED→BLOCKED`.
- `_validate_review_approval_conn` — for a subject bound
  `REDERIVED_AT_REVIEW`, **requires** `rederived_artifact_refs` and requires
  them to equal the bound `artifact_refs` (`REVIEW_REDERIVATION_REQUIRED`,
  `REVIEW_REDERIVATION_MISMATCH`, `INVALID_REDERIVED_ARTIFACT_REF`).
- `runtime/cli.py:247-251` + `:615-620` — `maps review-record TASK REVIEWER
  VERDICT --summary S`. Passes only those four args to `record_review`. **No
  `--rederived-artifact-ref` argument.**

### 1b. The gaps (from `traj12-next3-scoping.md` §Item #2)

1. **`record` (verdict):** a consequential task bound `REDERIVED_AT_REVIEW`
   **cannot be approved via CLI** — `record_review` always returns
   `REVIEW_REDERIVATION_REQUIRED` because no CLI path passes the re-derived
   refs. The store primitive is complete; the composition/CLI surface is not.
2. **`recover`:** there is **no review lease/heartbeat/expiry**
   (`/usr/bin/grep -rn "review.*lease\|reviews.*expire" runtime/state/*.py` →
   nothing). A reviewer who claims and vanishes leaves the review permanently
   stuck behind `idx_reviews_one_open`. Recovering it means force-closing
   another identity's open review — **a new authority**.
3. **`release`:** the roadmap's `flow release-check` (§12.3) is
   verify-approved-subject → validate-artifact-identity → release-path-smoke →
   operator-visible-summary. No primitive exists for "release-path smoke" or
   "artifact identity validation"; this is an **operator-visible-release
   authority surface** (`OPERATOR_VISIBLE_RELEASE_CHECK` review type), not a
   plain composition.
4. **`handoff`:** the roadmap's `flow handoff` (§12.3) ends in "attach/start
   replacement session" — **provider launch**, which `flow start` deliberately
   excludes. The continuity-link + review-independence-consequence part is
   composable, but a scoped "handoff that stops before session launch" needs
   its boundary defined and overlaps `runtime/state/helper_recovery_lineage.py`.

## 2. Smallest first slice: `maps flow review-record`

### 2a. What it is

A bounded lifecycle flow, sibling to `flow review-start`, that records a review
verdict as a **pure composition over `record_review`** — adding exactly the one
missing piece: freshness-mode-aware re-derived artifact refs.

`runtime/flow_review.py::flow_review_record(store, task_id, *, reviewer_id,
verdict, summary, rederived_artifact_refs=())`:

1. **Preflight.** Resolve the open review for `(task_id, reviewer_id)`
   (`_open_review_for` already exists in `flow_review.py`). If none →
   `_failed("preflight", NO_OPEN_REVIEW)`.
2. **Freshness-mode check.** Read the bound review subject
   (`store.get_review_subject(review_id)`). If it is bound
   `REDERIVED_AT_REVIEW` and `rederived_artifact_refs` is empty →
   `_failed("rederivation_preflight", REVIEW_REDERIVATION_REQUIRED)` — a
   deterministic, early, legible failure instead of a deep hook error.
3. **Record.** `store.record_review(task_id, reviewer_id, verdict, summary,
   rederived_artifact_refs=rederived_artifact_refs or None)`. All real
   enforcement stays in the store primitive — the flow adds no checks of its
   own, only argument plumbing + an early preflight mirror.
4. **Stop.** Return `{"ok": True, "code": "FLOW_REVIEW_RECORDED", "verdict": …,
   "new_status": …, "review": …}`. No outcome recording, no next-task
   dispatch, no session action.

### 2b. CLI

`maps flow review-record TASK_ID --reviewer-id R --verdict {APPROVED,
CHANGES_REQUESTED,BLOCKED} --summary S [--rederived-artifact-ref REF ...]`

added to the existing `flow` subparser (`runtime/cli.py:285` `flow_sub`),
alongside `flow start` / `flow review-start`.

**Leave `maps review-record` as-is** — it stays the thin store passthrough. The
flow verb is the freshness-aware path. (Alternatively `--rederived-artifact-ref`
could be added to `maps review-record` directly; the design recommends the flow
verb so the `flow review-start` → `flow review-record` pair is a coherent
deterministic sequence and `review-record` stays a minimal primitive wrapper.
Either is acceptable — implementer's call, noted in the impl task.)

### 2c. Why this clears the §12.2 promotion bar

1. repeated — every independent review ends in a recorded verdict;
2. stable steps — one store call + one preflight;
3. mechanically observable success/failure — `record_review`'s `MutationResult`;
4. exceptional branches known — the `record_review` error codes (1a);
5. authority checks already exist — entirely in `record_review` /
   `_validate_review_approval_conn`, unchanged;
6. reduces real friction — it makes `REDERIVED_AT_REVIEW` approvals possible
   from the CLI at all, and gives `flow review-start` a matching close.

## 3. Deferred verbs — what each needs before it can be dispatched

### `recover` — NEEDS an authority decision

There is no review lease. To recover a stuck review you must force-close or
reassign another identity's open review row. Questions for a future design /
operator:

- **Who** may recover a review claim? (coordinator only? any independent
  identity? an operator CLI?)
- **Trigger** — is there a review staleness signal at all, or is it always
  explicit ("this reviewer is gone, release it")?
- **Audit** — does the recovered review row become `completed_at`-stamped as
  `ABANDONED` (new verdict-like value → touches the `reviews` schema /
  `verdict` CHECK) or is it deleted (loses history)?

This is not a plain composition and likely needs a small schema touch — out of
scope for the "no schema" slice.

### `release` (`flow release-check`) — NEEDS design + is an operator-visible surface

Maps to `OPERATOR_VISIBLE_RELEASE_CHECK`. Needs: a spec for "artifact identity
validation" and "release-path smoke" as composable/checkable steps, and an
"operator-visible summary" sink. This is closer to a new capability than a flow
over existing ops. Separate design note when 6.21 gets prioritised past slice 1.

### `handoff` (`flow handoff`) — NEEDS a boundary decision

The composable part (freeze state + continuity link + review-independence
consequence) overlaps `runtime/state/helper_recovery_lineage.py`. The final step
(attach/start replacement session) is provider launch, which the `flow start`
precedent excludes. A scoped `flow handoff` that **stops before session launch**
(producing a continuity link + a ready-to-claim replacement task) is plausible
as a later slice; its stop boundary must be specified first.
