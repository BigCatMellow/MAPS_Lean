## 2. What `maps flow release-check` is

A bounded lifecycle flow that **assembles the operator-visible release verdict
inputs** for a task whose `review_required == "OPERATOR_VISIBLE_RELEASE_CHECK"`,
composing the three existing primitives over **explicitly caller/operator-supplied
evidence** (none of the primitives acquires or executes anything), and stops
before recording the review verdict.

It is **not**: an acquirer (it runs no download/install), a test runner (it
executes no scenario), or an approver (it records no verdict — see §5 for why
that is the recommended boundary and §6 for the decision).

---

## 3. The three checkable steps — spec

Each step consumes evidence the caller supplies (a JSON path or inline), calls
the existing pure evaluator, and contributes a `{state, report_ref}` fragment to
the composite. A step is **skippable only via an explicit
`allow_not_applicable` / `NOT_APPLICABLE`** declaration, never by omission.

### Step 1 — verify approved subject

Read the bound review subject (`store.get_review_subject(review_id)` for the
task's open `OPERATOR_VISIBLE_RELEASE_CHECK` review). Fail
`RELEASE_CHECK_NO_BOUND_SUBJECT` if absent (the review-binding layer already
mandates it, so this is a legibility guard). Carry the subject's `run_id` /
`artifact_refs` / `freshness_mode` forward — they are the identity anchor Step 2
validates against.

### Step 2 — validate built/acquired artifact identity

Input: a `maps-acquisition-paths-v1` **manifest** (operator-authored, in-repo or
supplied) + **observations** (caller-supplied: what was actually seen at each
path). Call `evaluate_acquisition_evidence(manifest, observations, label=<task>-release)`.

- Manifest `expected_ref` for each path is the operator's committed intent;
  observation `observed_ref` is what the releasing party saw.
- Composite fragment = the report's `_aggregate` state (`PASS` / `FAIL` /
  `UNKNOWN`), `report_ref = acquisition-report:<sha256>`.
- A task with no acquired artifacts (pure in-repo code change) supplies a
  manifest whose single path is `kind: OPERATOR_ARTIFACT`, `allow_not_applicable:
  true`, observed `NOT_APPLICABLE` with a `not_applicable_decision_ref` — the
  primitive already supports this. It is **declared N/A, not skipped.**
- Cross-check: if the bound review subject has a `run_id`, additionally run
  `verify_git_run(store, run_id, repo_root=…)` and fold its verdict into the
  fragment (git-worktree identity of the reviewed code artifact). **OPEN
  QUESTION §7**: whether Step 2 requires the git cross-check or treats it as
  optional evidence.

### Step 3 — run release-path smoke

Input: a frozen benchmark **protocol** + caller-supplied **scenario results**.
Call `evaluate_benchmark_results(protocol, results, label=<task>-release-smoke)`.

- Composite fragment = `benchmark_status` (`COMPLETE` / `FAIL` / `INCOMPLETE`),
  `report_ref = <sha256>` of the results.
- The protocol's mandatory `real_external_or_operator_visible_scenario` is the
  "operator-visible" part of the roadmap phrase — the release smoke must include
  at least one scenario an operator can see the result of.
- **OPEN QUESTION §7**: full protocol vs. a designated `release-smoke`
  minimal protocol vs. allowing `runtime.smoke` as the floor for
  code-only releases.

### Step 4 — record operator-visible summary

Compose a summary object:
```
{
  "release_check_version": 1,
  "task_id": …,
  "review_id": …,
  "subject_run_id": …,
  "artifact_identity": {"state": <PASS|FAIL|UNKNOWN|NOT_APPLICABLE>, "report_ref": …},
  "release_smoke":     {"state": <COMPLETE|FAIL|INCOMPLETE|NOT_APPLICABLE>, "report_ref": …},
  "composite": <READY_FOR_OPERATOR_VERDICT | BLOCKED>,   # BLOCKED iff any FAIL
  "recorded_at": …
}
```
`composite == BLOCKED` iff Step 2 or Step 3 is `FAIL`. `UNKNOWN` / `INCOMPLETE`
→ `READY_FOR_OPERATOR_VERDICT` (the operator weighs the gap; the flow does not
decide).

**Where it is recorded — OPERATOR DECISION (§6).** The flow returns the summary
in its payload regardless; whether it is *persisted* (and where) is the
decision.

### Return shape (family convention)

```
{"ok": true, "code": "FLOW_RELEASE_CHECK_ASSEMBLED",
 "task_id", "review_id", "summary": {…§Step-4…},
 "next_step": {"state": "STOPPED_BEFORE_RELEASE_VERDICT",
   "reason": "flow release-check assembles the artifact-identity + release-smoke
     evidence for the operator-visible review; it records no verdict — the
     operator/reviewer runs `maps flow review-record` with the summary in hand.
     composite=<…>"}}
```
Failure of any step → `_failed("<step>", …)` (reuse `flow_review._failed` /
`flow_handoff` pattern) with the offending evaluator error surfaced verbatim.

## 5. Why the flow must STOP before the verdict (recommended boundary)

The roadmap sequence ends at "record operator-visible summary", not "record
verdict". `flow review-start` set the precedent (stop before verdict);
`flow review-record` (PR #218) is the deliberate, separately-invoked verdict
step with its own re-derivation gate.

A `flow release-check` that composed through to `record_review APPROVED` on
green evaluators would **remove the human from an operator-visible release** —
the exact thing `OPERATOR_VISIBLE_RELEASE_CHECK` exists to prevent. The
evaluators consume *caller-supplied* evidence; trusting that evidence enough to
auto-approve defeats the review type.

**Recommended:** `flow release-check` assembles + returns (+ optionally persists)
the summary and **stops**. The operator/reviewer then runs `maps flow
review-record` with the summary as input. A `composite == BLOCKED` summary is
strong input for a `CHANGES_REQUESTED` / `BLOCKED` verdict but the flow does not
force it (see §6 for whether it *should*).

## 6. OPERATOR DECISION REQUIRED

Three decisions gate a `flow release-check` impl slice. None can be resolved in
a design note.

1. **The summary sink.** Reuse `record_review.summary` (a free-text string — the
   composite would be JSON-in-a-string) / `record_outcome.notes` (post-DONE
   surface, so timing is wrong) / **a new `release_checks` table** (structured,
   audit-clean — a `schema.sql` change). Recommendation: a new append-only
   `release_checks` row keyed by `(task_id, review_id)` holding the acquisition
   report ref, the smoke report ref, the composite state, and — if decision 3
   says so — an operator acknowledgement ref. This is a **schema decision**.

2. **Do the evaluator reports persist?** `evaluate_acquisition_evidence` /
   `evaluate_benchmark_results` are pure functions today; their reports are
   content-addressed but stored nowhere. For a release audit trail the reports
   (or at least their `report_ref` + the input evidence refs) should persist.
   Where — the `release_checks` row, an evidence-ref table, the review subject?

3. **Is a `composite == BLOCKED` release-check advisory or blocking?** Options:
   (a) advisory — the reviewer sees `BLOCKED` and chooses the verdict; (b)
   hard — `record_review` refuses `APPROVED` for an
   `OPERATOR_VISIBLE_RELEASE_CHECK` task unless a non-`BLOCKED` release-check
   summary exists (a new gate in `_validate_review_approval_conn`, analogous to
   the criterion-verification and bound-subject gates). (b) is the stronger
   guarantee but adds an approval-path dependency on the release-check having
   run — an authority-model change.

4. **Who may run `flow release-check`?** The releasing party, the reviewer, an
   operator, any of them? (It records no verdict, so it is low-authority — but
   if decision 3(b) makes it approval-gating, "who ran it" matters.)

## 7. OPEN QUESTIONS (design-level, not operator authority)

- **"release-path smoke" scope** — full frozen benchmark protocol / a
  designated minimal `release-smoke` protocol / `runtime.smoke` as the floor
  for code-only releases (§1c, §Step 3).
- **Step 2 git cross-check** — required, or optional evidence (§Step 2).
- **Evidence input format** — a single `--evidence-json <path>` bundle
  (manifest + observations + protocol + results), or four separate flags?
  The `flow` subparser precedent (`flow start` / `review-start`) uses repeatable
  scalar flags; a release-check's inputs are structured, so a JSON bundle is
  likely — but that diverges from the family CLI shape.
- **`NOT_APPLICABLE` for a whole step** — a pure code change with no acquired
  artifact and no release smoke: does `flow release-check` still require both
  steps declared N/A, or can a task's contract mark the check code-only?
- **Interaction with `record_review`'s `REDERIVED_AT_REVIEW` re-derivation** —
  if the review subject is `REDERIVED_AT_REVIEW`, are the release-check reports
  part of what must be re-derived at verdict time?

## 8. Verdict

**`flow release-check` is NOT dispatchable as an impl slice yet — it stays
PARKED pending the §6 operator decisions**, primarily (1) the summary sink /
schema and (3) advisory-vs-blocking. Unlike `handoff` (which needed only a
design decision and shipped in #231), and like `recover` (operator + schema),
`release` genuinely needs operator input before code.

**But the design is now concrete**, and #224 §1b's "closer to a new capability"
is **corrected**: the two hard evaluators exist; what remains is one composition
+ a sink decision + an authority decision. Once §6 lands, the impl is a
~120-line `runtime/flow_release_check.py` + CLI + tests, comparable to
`flow_handoff` plus whatever the sink decision adds.

`recover` stays PARKED (operator + `reviews`-schema decision, unchanged —
`work/notes/2026-09-01-6.21-next-increment-scoping.md` §1a).
