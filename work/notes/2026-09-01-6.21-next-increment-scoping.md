## 1. Re-verified state of the three deferred verbs

Source: `work/notes/2026-09-01-6.21-review-lifecycle-verbs-design.md` §3, checked
against merged code.

### 1a. `recover` — STILL BLOCKED. Authority decision **and** schema.

The design note said "no review lease; force-closing another identity's open
review is a new authority; likely a small schema touch." Re-verified:

- **No review-release primitive of any kind exists.**
  `/usr/bin/grep -rn "def .*review" runtime/state/*.py` (excl. tests) → the only
  review mutations are `claim_review`, `claim_review_with_subject`,
  `bind_review_subject`, `record_review`. There is no `release_review` /
  `abandon_review` / un-claim.
- **The narrower "a reviewer voluntarily releases their *own* open review" is
  also blocked** — it still needs a brand-new store mutation (dispatch forbids
  new primitives) and a schema decision: the `reviews` table has only
  `completed_at` + `verdict` (`APPROVED`/`CHANGES_REQUESTED`/`BLOCKED`), no
  released/abandoned state. Deleting the row loses history; adding a state
  touches the `verdict` CHECK / a new column.
- The `idx_reviews_one_open` partial unique index means a stuck open review
  genuinely wedges the task until it is force-closed — real, but not fixable
  without the above.

**Verdict: unchanged. `recover` needs an operator/authority decision (who may
force-close another identity's review, on what trigger, with what audit
outcome) + a `reviews`-schema decision. Not this increment.**

### 1b. `release` (`flow release-check`) — STILL BLOCKED. Needs its own design note.

`OPERATOR_VISIBLE_RELEASE_CHECK` is a live `review_required` value
(`runtime/state/common.py:11` `VALID_REVIEW`), and a task carrying it already
routes through the full `flow review-start` → `flow review-record` sequence with
a **mandatory** bound review subject (`review_binding.py:68`
`_requires_bound_subject_conn` → always True for that value). So the *review*
half of a release check is already covered by slice 1.

What `flow release-check` adds per the roadmap (§12.3) is genuinely new and has
no primitive: "artifact identity validation", "release-path smoke", and an
"operator-visible summary" sink. None of these is a composition over an existing
op. The design note's own words: "closer to a new capability than a flow over
existing ops."

**Verdict: unchanged. `release` needs a dedicated design note first (spec the
three new checkable steps + the summary sink). Not this increment, and not a
one-PR slice.**

### 1c. `handoff` (`flow handoff`) — STILL BLOCKED, but on a **design** decision, not an operator one.

The composable primitives exist: `runtime/state/helper_recovery_lineage.py`
provides `record_run_helper_link` / `record_run_recovery_link` (+ getters/
listers) — the "continuity link" surface — and a replacement task is
`create_task` + `update_contract`. The review-independence consequence is
automatic once a lineage link is recorded (the continuity-component check in
`record_review` / `claim_review` reads it).

What is unspecified — and what the design note means by "its stop boundary must
be specified first":

- **What state actually changes?** There is no "handed-off" task/run state. Does
  `flow handoff` release the outgoing worker's claim (`heartbeat` expiry? an
  explicit release? — no release-claim primitive exists either, same gap as
  `recover`), or leave it and just record the link?
- **What does the replacement task carry?** A copy of the contract? A pointer to
  the frozen run? Its own fresh review requirement?
- **Where is the stop line** — "produces a continuity link + a ready-to-claim
  replacement task" vs. the excluded "attach/start replacement session"?

**Verdict: `handoff` needs a design note to specify the stop boundary and the
state-change semantics. It does *not* need an operator decision (unlike
`recover`/`release`) — the primitives are all there. This makes a `flow handoff`
design note the natural increment *after* the hardening pass below.**

## 2. Chosen increment: **(a) — `flow review-start` → `flow review-record` coherence + hardening pass**

Per the dispatch priority order: (b) yields no no-authority/no-schema sub-slice
(§1a–1c), and (c) PARK is not warranted because (a) is a real, non-manufactured
increment. Three concrete items, all in `runtime/flow_review.py` +
`tests/test_flow_review.py`, **no authority, no schema, no status flip**:

### 2a. `flow_review_record` output is missing the deterministic-flow `next_step` block

`flow_start` (`runtime/flow_start.py:178`) and `flow_review_start`
(`runtime/flow_review.py`) both return
`next_step: {"state": "STOPPED_BEFORE_…", "reason": "<what this flow does NOT
do>"}`. `flow_review_record` returns `code`, `verdict`, `new_status`, `review`,
`record` — **no `next_step`**. It is a terminal verb, but it still deliberately
does not record real-world outcomes or dispatch follow-on work (docstring step
4). The family convention is that every `maps flow` verb states its stop
boundary in a machine-readable `next_step`; the terminal verb breaks it.

**Fix:** add `next_step: {"state": "REVIEW_RECORDED", "reason": "flow
review-record does not record real-world outcomes (maps outcome-record) or
dispatch follow-on work; the task is now <new_status>"}`. Purely additive to the
output dict — `_emit` json-dumps it, consumers keying on `code`/`new_status` are
unaffected.

### 2b. Latent `int(review["id"])` fragility in `flow_review_record`

After `store.record_review(...)` succeeds, the flow does
`closed = _review_by_id(store.list_reviews(task_id), int(review["id"]))`. When
the caller does **not** hold an open review (`review is None`, the non-owner /
no-open-review path added in #220), `record_review` returns
`NO_OPEN_REVIEW`/`NOT_REVIEW_OWNER` and `if not recorded.ok: return` fires first
— so `int(review["id"])` is currently unreachable with `review is None`. But it
is one `record_review` ownership-logic change away from a `TypeError`.

**Fix:** derive the closed review from the reviewer id + task
(`_open_review_for` won't work — it's closed — so re-scan `list_reviews` for the
most recent completed review by that reviewer), or guard
`review is not None` explicitly. No behaviour change on any currently-reachable
path.

### 2c. No module-level start→record coherence e2e

`tests/test_flow_review.py` (post-#218/#220) has piecewise `FlowReviewRecordTests`
cases and **one** CLI end-to-end. It does not have a `flow_review`-module-level
assertion that *the subject `flow_review_start` binds is exactly the one
`flow_review_record` validates against* — the coherence property of the pair.

**Fix:** add two module-level sequence tests: (i) `flow_review_start(freshness_mode=
"REVISION_BOUND", artifact_refs=[X])` then `flow_review_record(verdict="APPROVED")`
→ `DONE`, asserting the recorded review's subject id matches the started one;
(ii) `flow_review_start(freshness_mode="REDERIVED_AT_REVIEW", artifact_refs=[X])`
then `flow_review_record(verdict="APPROVED", rederived_artifact_refs=[X])` → `DONE`,
and the same with `rederived_artifact_refs=[Y]` → `record` / `REVIEW_REDERIVATION_MISMATCH`.
