## 2. Why that is not sufficient for DONE

Per-category exact rate (from the run):

| Category | Exact rate |
|---|---|
| DIRECT | 1.00 |
| PARAPHRASE | 1.00 |
| MULTI_SKILL | 1.00 |
| NO_SKILL | 1.00 |
| **VOCABULARY_SHIFT** | **0.00** (4/4 missed activations) |
| **HARD_NEGATIVE** | **0.00** (4/4 false activations) |
| **AMBIGUOUS** | **0.00** (no disambiguation signal) |

Three of the six failure classes §6.9's own "Routing evaluation must include"
list enumerates score **0.00**. A routing capability is not `DONE` when it is:

1. **blind to synonym shifts** (`VOCABULARY_SHIFT` 0/4) — the same task intent
   in different words is not routed at all;
2. **without any relevance judgement** (`HARD_NEGATIVE` 4/4 false activations) —
   the selector fires on *any* accidental shared token; it has no notion of "is
   this Skill actually relevant";
3. **unable to disambiguate** (`AMBIGUOUS` — flat SELECT list, no confidence).

The trajectory playbook's status-truth rule (`ROADMAP_TRAJECTORY_CHECK.md`
"Roadmap/status truth rule" + roadmap §17.3): *"do not mark work DONE from
formatting/prose review alone"* and *"Do not mark a capability implemented
because a document describes it."* The document — a frozen eval — now exists;
the capability it measures fails half its own acceptance categories. Flipping
to DONE on that basis is exactly the anti-pattern those rules name.

## 3. The optional §criterion (scoping note §1d) — where the measured result lands

The scoping note proposed an optional numeric criterion (a reviewer's call, not
§6.9-mandated). Measuring against its shape:

1. **Coverage ≥ 4 per category** — **MET** (5/4/4/4/4/4).
2. **Precise-vocabulary categories hold** (DIRECT + PARAPHRASE + MULTI_SKILL +
   NO_SKILL) — **1.00 across all four**; clears any reasonable floor.
3. **Hard-negative / no-Skill false-activation cap** — **4/4 hard negatives
   false-activate** (`NO_SKILL` is clean). For this reviewer this is the item
   that blocks DONE: a selector with *zero* relevance judgement, false-firing on
   every accidental token overlap, is not a promotable routing capability
   regardless of the downstream trust gate. The trust gate (6.22) + SEC4
   quarantine bound the *safety* blast radius (a false activation surfaces a
   Skill as trust-gated evidence, not an execution) — but they do not make the
   routing *correct*, and 6.9 is the routing-correctness capability.
4. **Aggregate `selection_f1`** — **0.722**. Middling; on its own arguable
   either way for a P2.

Item 3 is dispositive. **NO FLIP.**

## 4. Mitigations acknowledged (they bound the risk, not the verdict)

- Downstream containment: 6.22 trust gate + SEC4 quarantine sit *after*
  selection, so a false activation is trust-gated evidence, never a silent
  execution. A missed activation costs recall, not safety.
- The gaps are **pinned, not tuned away** — `test_exp_b_skill_routing.py`
  fails on any selector change that shifts the balance, so a future improvement
  has a real acceptance test.
- The frozen corpus + harness are reusable: the next 6.9 slice re-runs EXP-B as
  its gate.

These are why the situation is "IN PROGRESS with a clear next step", not
"CUT SCOPE" or "STOP".

## 5. What DONE requires (recorded for the next 6.9 slice)

Either:

- **(a) selector-quality work** — a separate, reviewed PR to `_select_skills`
  adding at least: near-synonym / stopword handling (for `VOCABULARY_SHIFT`),
  a relevance threshold instead of any-token-overlap (for `HARD_NEGATIVE`), and
  optionally a confidence signal enabling an `AMBIGUOUS` outcome. Re-run EXP-B

  number). Then re-run this gate step; **or**
- **(b) an explicit operator sign-off** under §17.3 that the characterized
  behaviour (perfect on precise vocabulary; blind on synonym / hard-negative /
  ambiguity, with the downstream trust-gate containment) is acceptable to
  promote `6.9` / `S6` as-is — recording that decision as the DONE evidence.
  This is available (§17.3) but has not been made; a reviewer should not assume
  it.
