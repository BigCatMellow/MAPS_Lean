# Design: `require_write_scope_binding` — the opt-in signal, no enforcement

Roadmap 6.4. Direct follow-up to
`work/notes/2026-09-15-6.4-verify-git-run-enforcement-design.md` (PR #361),
which named two ways to eventually wire `verify_git_run`'s scope-check into
a Hook guard and stopped without choosing. Coordinator `venu` decided
**(B): add a genuine opt-in flag first**, default-off, mirroring
`require_worktree_binding` — "matches every other enforcement seam in this
project (`CANONICAL_RUN`, `--enforce-validation`, `--enforce-canonical-run`
all default-off opt-in)... (A) enforcing against the implicit default would
gate every run including your own PR #360's 4-area shape — that is exactly
the silent-scope-expansion rule 9/10 exists to block."

**Scope: schema + API flag only. No `runtime/policy/` change, no guard, no
enforcement. This slice's entire job is giving a future guard something
clean to no-op on for every run that doesn't ask for it — exactly what
`base_revision`/`require_worktree_binding` already give `CanonicalRunGuard`
today, and exactly what PR #361 §2 found `readable_scope`/`writable_scope`/
`forbidden_scope` do not currently have.**

## Why a plain boolean column, not a second table

`run_worktree_bindings` is a separate table because worktree identity is
several fields (`repo_root`, `git_common_dir`, `git_dir`,
`worktree_private_dir`, `head_revision`) and its *row's existence* is the
opt-in signal a guard checks (`manifest.get("worktree")` is `None` unless a
row exists). Write scope has no equivalent multi-field identity to store —
`readable_scope`/`writable_scope`/`forbidden_scope` already exist as
columns on `run_manifests` itself and are always populated (PR #361 §2).
What's missing is purely a **boolean**: did the caller consciously declare
this run's write scope as something a future guard should enforce, or is
what's stored just the untouched default. A single new column on the
already-immutable `run_manifests` table is the right level of structure —
no join, no second immutable-trigger pair to write, no second table whose
only content is one bool.

## Schema

```sql
-- runtime/state/schema.sql, run_manifests table
write_scope_binding_required INTEGER NOT NULL DEFAULT 0
```

`0`/`1` (sqlite has no native bool), cast to Python `bool` in
`get_run_manifest`'s returned dict, same treatment `readable_scope` etc.
get for their JSON columns. `DEFAULT 0` means every *existing* row this
project has ever created (there is no migration tool in this codebase —
confirmed, `/usr/bin/grep -rn "ALTER TABLE" runtime/state/*.py` has zero
hits, schema.sql is applied once via `CREATE TABLE IF NOT EXISTS` on a
fresh DB) would read back `False` if re-created from the new schema, which
is the correct fail-closed default for a signal a future guard will use to
decide whether to even look.

## API surface — mirrors `require_worktree_binding` exactly, one flag, no companion requirement

Unlike `require_worktree_binding` (which fails loudly if `base_revision` is
missing, because worktree identity has a genuine unpopulated state that
flag alone can't create), `require_write_scope_binding` needs **no
companion validation**: `readable_scope`/`writable_scope`/`forbidden_scope`
are already always computed and stored regardless of this flag (PR #361
§2), so there is nothing this flag could request that isn't already
present. Setting it simply records "yes, treat this run's already-computed
scope as something to enforce later" — including the common case where the
caller passed no explicit `writable_paths` and is relying on the default
(the task's own `output_paths`), which is a perfectly legitimate thing to
opt into enforcing.

- `TaskStore.create_run_manifest(..., require_write_scope_binding: bool = False)`
  — threads straight into the `INSERT INTO run_manifests` column/value
  lists, no branching logic needed (contrast `require_worktree_binding`,
  which gates a `RuntimeError`/fail-loud branch).
- `flow_start(..., require_write_scope_binding: bool = False)` and
  `flow_start_from_runtime_limit_args(..., require_write_scope_binding: bool = False)`
  in `runtime/flow_start.py` — pass-through, same shape as the four
  existing `require_worktree_binding` threading points.
- `maps flow start --require-write-scope-binding` (`runtime/cli.py`,
  `action='store_true'`, next to the existing `--require-worktree-binding`
  argument).
- `runtime.integrity.cli run-create --require-write-scope-binding`
  (`runtime/integrity/cli.py`, same shape).

## What this does NOT do (non-goals, explicit)

- No guard reads this flag. `CanonicalRunGuard` is untouched.
  `runtime/recovery/production.py` is untouched. Setting the flag today has
  **zero behavioral effect** beyond the value being persisted and readable
  back via `get_run_manifest`/`run-show` — verified by construction (no new
  code path consults it).
- Does not resolve PR #361's fork (A) vs (B) enforcement question beyond
  "(B), so build the opt-in first" — a later, separate slice designs and
  wires the actual guard consulting this flag once it exists, at which
  point the guard can safely no-op (`if not manifest.get("write_scope_binding_required"): return None`)
  for every run that didn't ask, exactly mirroring
  `_require_bound_worktree`'s shape.
- No retroactive backfill of the flag onto already-created runs (none
  exist that matter — PR #361 §3 already found the only local `.maps/`
  task data available is two stale exercise rows).
- Does not touch `verify_git_run`, `git_scope.py`, or the scope-comparison
  logic itself — those already work and are unmodified.

## Verification

A fresh reader can, from this note alone: (1) add the column to
`schema.sql`, (2) thread `require_write_scope_binding` through
`create_run_manifest`/`flow_start`/`flow_start_from_runtime_limit_args`/both
CLIs exactly as `require_worktree_binding` is threaded (same call sites,
same parameter position), (3) cast the column to `bool` in
`get_run_manifest`, (4) write tests mirroring
`tests/test_execution_integrity.py`'s worktree-binding tests: default
`False` when omitted, persists `True` when passed, round-trips through
`get_run_manifest`, and a source-guard test confirming no file under
`runtime/policy/` or `runtime/recovery/` references the new column/flag
name (proving the "no enforcement wiring yet" boundary held).
