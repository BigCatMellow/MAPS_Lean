Roadmap 6.4 (`work/roadmaps/CAPABILITY_CHECKLIST.md` row 6.4, master spec
`work/roadmaps/agent-harness-capabilities/04-agentic-security.md` §6.1-§6.4).
Row 6.4's own text: "= H3 (registry done) + SEC3 (`CANONICAL_RUN` +
`DESTRUCTIVE_EXTERNAL_ACTION` enforcement ...). Capability-declaration
manifest + write/credential guards not built." Dispatched by coordinator

## 1. Re-verified: what "not built" actually covers, read from source

`git log --oneline -20 -- runtime/policy/` confirms nothing has touched
`runtime/policy/` since PR #310 (2026-09-12, the 6.22 `send()` call site) —
row 6.4's own last "Updated 2026-09-09" entry is still current; nothing
closed since.

`work/roadmaps/agent-harness-capabilities/04-agentic-security.md` §6 lists
seven gate points; only two have a built guard today (§6.2 "Before
destructive action" -> `DestructiveExternalActionGuard`, §6.7 "Before
session resume/recovery" -> `CanonicalRunGuard`; §6.6 "before persistent
guidance promotion" is 6.22's `MemoryProvenanceGuard`, a distinct row). Row
6.4's stated gap is specifically:

- §6.1 "Before write" — validate writable/forbidden scope.
- §6.4 "Before credential use" — validate declared credential capability.
- a "capability-declaration manifest" (ambiguous name — see §2 below).

## 2. The "capability-declaration manifest" phrase is a false lead — it names a different, already-in-progress roadmap item

`/usr/bin/grep -rn "capability.declar"` hits
`work/notes/2026-09-01-sec4-capability-declaration-manifest-design.md` and
its slice-1/2/3 implementations (`runtime/skills/capability_policy.py`,
`runtime/skills/gate.py`, PRs #219/#225/#242). That is **SEC4 / roadmap
6.10** — declared capability tokens for *Skills* (what a Skill body may
invoke), a separate system already three slices deep. Row 6.4's own text
reuses the same English phrase for a different, still-unbuilt concept (what
a *task/action* may do), but no note or code anywhere names a 6.4-scoped
"capability-declaration manifest" distinct from SEC4's. Re-dispatching or
re-designing this phrase as if it were 6.4-specific unbuilt work would
duplicate/conflate two systems. **Not attempted here** — this note scopes
only the two concrete gate points (§6.1, §6.4), not a new manifest concept.

## 3. Credential guard (§6.4 "Before credential use"): not buildable on real evidence today — naming why, not attempting it

Re-verified against source, not inferred: `/usr/bin/grep -rniE "credential"
runtime/` turns up exactly one place credentials are discussed as
*authority data* — none. There is no `task.policy.credential_*` field, no
credential broker, no secret-material handling anywhere in `runtime/`
(`runtime/skills/gate.py`'s `CREDENTIAL_ENVIRONMENT_ACCESS` finding is a
static-text scanner over Skill *bodies*, a different SEC4 surface, not an
authority record a guard could consult). The master roadmap is explicit
that this is intentional, not an oversight: `04-agentic-security.md`
**SEC6 — Credential broker experiment**, "Only if credential-bearing tasks
become common/high-risk enough" — i.e. this system has decided credential
handling is not yet justified, full stop.

Building a `CredentialGuard` now would mean inventing a fictional
`task.policy.credential_capability`-shaped field with no real producer or
consumer anywhere, purely so the guard has something to compare against —
authority-data fabrication, the same category of thing this dispatch's
predecessor was explicitly warned off (don't fabricate to force a branch to
exist). Per rule 8 (smallest change, no infrastructure for a one-off need)
and rule 13 (no permanent machinery before repeated evidence justifies it):
**not scoped into this slice.** SEC6 gates it; nothing here changes that
gate.

## 4. Write guard (§6.1 "Before write"): real authority data exists today — this is the buildable slice

Unlike credentials, a real, already-production authority field exists:
`task.output_paths` (`task_output_paths` table, `readiness.py` requires it
non-empty for `AGI READY`, and `runtime/helpers/common.py::path_in_scope()`
/ `validate_active_scope()` already implement the exact scope-membership
check — currently consulted only by the one-shot helper adapters
(`ollama.py`, `aider.py`), never by the Hook/guard system). This is real,
load-bearing, already-shipped authority data with an existing reusable
scope-check function — not invented.

`HookEvent.BEFORE_WRITE` / `AFTER_WRITE` already exist in the enum
(`runtime/harness/hooks.py`) with **zero references anywhere in
`runtime/`** outside that one enum definition — confirmed by
`/usr/bin/grep -rn "BEFORE_WRITE\|AFTER_WRITE" runtime/ --include="*.py"`.
They are unused, not merely unwired-but-referenced.

### 4a. Load-bearing finding: there is no real path to firing this guard without a separate, larger architecture decision

`HarnessService` (`runtime/harness/service.py`) only mediates *session
lifecycle* operations against an adapter: `start`/`send`/`resume`/`stop`.
There is no `HarnessService.write(...)` method, and none of those four
operations corresponds to "a file write happens." The actual file writes a
task performs happen *inside* an agent's own tool loop (Claude Code, or
whatever CLI is running the session) — a loop this harness does not mediate
or intercept at all today. `runtime/policy/memory_provenance_guard.py`'s
own docstring already named this precisely, for a sibling guard: *"No
[the tool-call event pair]/adapter tool-loop interception, no new
`HookEvent` member"* is listed as a deliberate non-goal of 6.22's own
guard. The same gap blocks this row's write guard identically — it is not
a 6.4-specific problem, it is a whole-harness architectural absence
(building an actual tool-call interception/proxy layer), and deciding
whether/how to build that is a materially larger design question than "add
one guard," squarely a design-authority call this note does not make.

**Consequence:** whatever is built in this slice will be composed but
**unwired** — same starting state `DestructiveExternalActionGuard` itself
shipped in (`10127f9`, "SEC3, unwired", before `d810509`/PR #194 gave it a
real firing site three weeks later via `HarnessService.stop()`). That
precedent is why building the guard now, honestly disclosed as unwired, is
still real incremental progress and not premature infrastructure: the
guard's *decision logic* is genuine and testable today (real
`task.output_paths`, real `path_in_scope()`), independent of when/whether a
firing call site is built.

**Correction, found while implementing this slice (rule 14 — don't let this
note's own prior claim outrank what a full re-check of source turns up):**
the claim above ("no real path to firing... without a separate, larger
architecture decision") is true only for `BEFORE_WRITE` specifically — it
is **not** true that no real write-scope signal exists at all.
`runtime/state/integrity.py::create_run_manifest` already stores a real
per-run `readable`/`writable`/`forbidden` scope contract (defaulting
`writable` to the task's own `output_paths`), and
`runtime/integrity/git_scope.py::verify_git_run` already does a real,
already-shipped post-hoc comparison of actual changed paths (`git diff`
against `base_revision`, plus untracked files) against that stored scope,
returning `out_of_scope`/`forbidden_changes`. It is exposed today only as
`runtime/integrity/cli.py run-verify-git` — advisory-on-request, "not
consulted by any dispatch flow," the exact same disclosed state the 6.16
row named for the sibling worktree-identity check before that check was
wired into `CanonicalRunGuard._require_bound_worktree` on an
already-fired event.

That precedent (6.16) is the honest template for how this row's write gap
*should* eventually close: wire `verify_git_run`'s comparison into a guard
on an already-fired event (`BEFORE_RESUME`/`SESSION_STOPPING`, the same
events `CanonicalRunGuard` already uses), not invent a self-declared
`write_paths` contract with no real producer. **Deliberately not done in
this slice**, named here instead of silently attempted: unlike composing an
inert, never-fired `BEFORE_WRITE` guard, wiring a new DENY-capable check
onto `SESSION_STOPPING`/`BEFORE_RESUME` would immediately change the
behavior of the already-partially-live `recovery-tick
--enforce-canonical-run` enforced-pass path for every run, the moment it's
composed — every run's actual git changes would start being compared
against its (usually implicit, defaulted-from-`output_paths`) writable
scope on every resume/stop, which could produce new denials on
previously-passing enforced passes. That is real behavior change on a path
with live operational use, not "add one more unused guard" — squarely a
bigger decision than this bounded slice's authority, and named here as the
concrete, well-grounded next step for whoever scopes it (rule 10 — don't
silently expand scope).

Given that, §4b below still ships the caller-declared `write_paths`
guard as the safe, zero-blast-radius part of this slice (real authority
data, real decision logic, composed-but-genuinely-inert) — but the
`verify_git_run` finding is the more important discovery of this note and
should drive whatever 6.4 dispatch comes after this one, not the
`BEFORE_WRITE` guard below.

### 4b. Guard shape — mirrors `DestructiveExternalActionGuard` exactly

New module `runtime/policy/write_scope_guard.py`, `WriteScopeGuard`,
duck-typed `source` (`get_task(task_id) -> dict | None`, same as the
destructive guard). Caller-declared contract, never inferred: the
about-to-happen write states `context["write_paths"]` — a non-empty list of
path strings — same self-declaration discipline as `destructive`/`external`
booleans (no static analysis, no filesystem sniffing of what the caller is
about to do).

Decision table (fixed, deterministic):

| Condition | Outcome |
|---|---|
| `write_paths` absent from context | DENY `WRITE_PATHS_REQUIRED` |
| present but not a non-empty list of non-blank strings | DENY `WRITE_PATHS_INVALID` |
| no `context["binding"]` (or missing `task_id`/`run_id`) | DENY `WRITE_BINDING_REQUIRED` |
| bound task cannot be read | DENY `WRITE_POLICY_UNAVAILABLE` |
| task's `output_paths` is empty/missing | DENY `WRITE_SCOPE_UNDECLARED` |
| any declared path resolves outside every entry of `task.output_paths` (via `path_in_scope()`, reused not reimplemented — rule 12) | DENY `WRITE_OUTSIDE_TASK_SCOPE` |
| every declared path is in scope | ALLOW `WRITE_WITHIN_TASK_SCOPE`, `evidence_refs=(task:<id>, run:<id>, paths:<...>)` |

`WRITE_SCOPE_UNDECLARED` is expected to be unreachable via any normal
`AGI READY` task (`readiness.py` already requires non-empty `output_paths`)
— named explicitly here, same fail-closed-defense-in-depth justification as
the destructive guard's own branches that only fire on malformed/legacy
task state. Stating this now so a future evidence-review note doesn't
have to re-derive it (rule 15 — don't hide it, say it up front).

Registration: `register_write_scope_guards(registry, guard)` on
`HookEvent.BEFORE_WRITE` only (one enforcement role,
`HookEnforcement.WRITE_SCOPE`). `AFTER_WRITE` is deliberately **not**
registered — a DENY-only guard gates nothing useful after the write already
happened; that event stays reserved for a future audit/evidence use, out of
scope here. Composed into `build_canonical_harness_service`
(`runtime/recovery/production.py`), same unwired-but-composed shape 6.22
slice 1 used, with the same kind of comment disclosing it changes no live
behavior yet.

### 4c. Isolation-test trap, named up front (rule: guard isolation test cross-reference)

`tests/test_destructive_external_action_guard.py::ProductionWiringTest`
scans every `runtime/**/*.py` file for the literal string
`"DESTRUCTIVE_EXTERNAL_ACTION"` and fails if it appears outside four named
files. This note and the new guard's own docstring must describe the
destructive-guard precedent **in prose**, never by pasting that literal
enum identifier (or `"MEMORY_PROVENANCE"`, guarded the same way by
`tests/test_memory_provenance_guard.py` if it has an equivalent scan — grep
it before writing the new module's docstring, not after). The new guard
gets its own equivalent `ProductionWiringTest`-shaped isolation tests
scoped to `"WRITE_SCOPE"` / `WriteScopeGuard` / `register_write_scope_guards`,
mirroring the existing pattern exactly.

## 5. Explicit non-goals

- No `CredentialGuard` — §3, no real authority data exists yet, gated by
  SEC6, not this dispatch's call to unblock.
- No capability-declaration manifest — §2, that name refers to a distinct,
  already in-progress roadmap item (6.10/SEC4), not 6.4.
- No tool-loop / `BEFORE_TOOL`/`AFTER_TOOL` interception — §4a, a separate,
  larger architecture decision, named but not decided here.
- No firing call site for `BEFORE_WRITE` — none can exist without the
  tool-loop decision above; this slice ships composed-but-unwired, exactly
  disclosed as such, same as SEC3's own starting state.
- Does not flip `CAPABILITY_CHECKLIST.md` row 6.4 to `DONE`. The write-guard
  half of the gap is what this slice closes; credential guard, the
  tool-loop architecture question, and (if it turns out to be genuinely
  6.4-scoped and not just 6.10 under a shared name) a capability-declaration
  manifest all remain open.
- No `AFTER_WRITE` registration — §4b.
