### 1b. `SkillDescriptor` carries resource **paths only** — no per-resource hash or size

`runtime/skills/format.py` `SkillDescriptor` (frozen, slotted):
`resource_paths`, `script_paths`, `reference_paths`, `asset_paths`,
`example_paths` — all `tuple[str, ...]` of relative posix paths.
`content_sha256` is a **whole-directory** digest (`_hash_snapshot`, lines
284–294: one `sha256` over every file's `relative\0len\0bytes\0`). There is
**no** per-file sha256 or byte-size field.

> **Correction to the dispatch's candidate (a):** it says "path + sha256 +
> bytes, already in `SkillDescriptor`". Only the **path** is already there.
> Per-resource sha256 and size are not — computing them needs `format.py` to
> hash each file at discovery (the bytes are already read by
> `_directory_hash` / `_verified_snapshot`; only the per-file digest is not
> currently kept), or `stat().st_size` for size alone (no read).

### 1c. There is no single-resource loader

`/usr/bin/grep -rn "def load_skill\|def load_catalog_skill\|resource" runtime/skills/format.py runtime/skills/catalog.py`
→ `load_skill(descriptor) -> SkillDocument` returns only
`SkillDocument(descriptor, body)` (SKILL.md text). `load_catalog_skill(entry,
store)` refuses non-activatable lifecycle states then returns `load_skill(...)`.
Neither returns any `scripts/` / `references/` / `examples/` / `assets/`
content. `_verified_snapshot(descriptor)` (lines 303–321) already reads **every**
file's bytes and verifies the whole-directory digest against
`descriptor.content_sha256`, returning `((Path, bytes), …)` — but nothing
exposes a single named resource from it.

### 1d. The 6.11 guardrail (`CAPABILITY_CHECKLIST.md` 6.11 row + `work/tasks/context-budget-classification-wave12.md`)

`budget_class` today "does not yet drive any actual load/fetch behavior
downstream". wave12's explicit escalation clause: *"any design where
`budget_class` is read by other code to decide what to load/fetch … requires
operator approval under 6.11's guardrail"*, and *"auto-loading MUST_LOAD items,
auto-fetching SHOULD_LOAD items"* crosses into "new retrieval-mechanism
territory". The roadmap guardrail: *"Explicit-first Context Builder remains
preferred until retrieval methods prove value in frozen evaluations."*

**What is and is not a guardrail violation:**
- Attaching a **listing** (paths the Skill already declares, plus size) is
  metadata — the same shape as `resource_paths` already being in the
  descriptor. **Not** retrieval.
- A **deterministic single-file read by exact declared path**, hash-verified,
  invoked **by a downstream consumer** (not by `_select_skills`) — the same
  shape as slice 1's `load_catalog_skill` body read — is **not** search /
  retrieval / a fuzzy fetch. It is the "if needed" in "only if needed".
- `_select_skills` eagerly reading resource **content** would be an expansion
  of what plan-assembly fetches → guardrail-adjacent. **Slice 2 does not do
  this.**

### 1e. Executable-content authority (dispatch STOP-condition check)

A LOAD-classified Skill has **already passed `assess_skill`** at catalog-build
(`register_skill_catalog` → gate report → lifecycle state). `assess_skill`
statically inspects every resource including scripts
(`EXECUTABLE_RESOURCE_PRESENT`, `SCRIPT_NETWORK_ACCESS`, `NETWORK_PIPE_EXEC`,
`_PRIVILEGE_RE`, `_DESTRUCTIVE_RE`, …) and QUARANTINEs on any BLOCK finding — so
a Skill whose scripts are dangerous is not `LOAD`, gets no body, and gets no
resource manifest. Slice 2 attaches the manifest / enables the loader **only
for gate-passed LOAD Skills**. It loads **no** content in `_select_skills` and
**does not execute** anything. There is **no new authority surface** — the gate
is the control, unchanged.

## 2. The seam

Same as slice 1: `runtime/context_builder.py::_select_skills`, inside the
existing `if decision.admission is MemoryAdmission.LOAD and store is not None:`
branch, **after** the body attach. Plus one small new function in
`runtime/skills/format.py` for the consumer-invoked "if needed" read.

`_select_skills` stays the plan-assembly point: it attaches the **manifest**
(no content) and nothing else. The manifest lists what a `LOAD` Skill's
`SKILL.md` body may reference; a downstream consumer (the task's executing
agent) pulls a specific resource **by exact path** through the new loader when
the procedure actually calls for it.

## 3. Smallest first slice — the execution-resource manifest

**Property made true in a real `maps flow start` run:**

> A matched `LOAD`-classified Skill's context-plan item carries
> `execution_resources`: an ordered list of
> `{"path", "kind", "bytes"}` for every `scripts/` / `references/` /
> `examples/` / `assets/` file the Skill bundles — **no content**. A downstream
> consumer can then read one named resource, hash-verified against the Skill's
> `content_sha256`, via `runtime.skills.load_skill_resource(descriptor,
> relative_path)`. `WITHHOLD` / `DENY` Skills carry no manifest.

### Impl surface (Phase 2 — NOT this note)

1. **`runtime/skills/format.py`**:
   - `load_skill_resource(descriptor: SkillDescriptor, relative_path: str) ->
     bytes` — validates `relative_path` is one of
     `descriptor.resource_paths` (reject anything else, incl. `SKILL.md`,
     traversal, absolute), then `_verified_snapshot(descriptor)` (hash-verifies
     the whole directory against `content_sha256`, raising `SkillChangedError`
     on drift) and returns the one file's bytes. Pure, no store, deterministic,
     single named file — not search.
   - Optionally a per-resource size helper for the manifest (`stat().st_size`,
     no read) — or fold size into `SkillDescriptor` at discovery. **Recommend
     `stat().st_size` at manifest-build time in `_select_skills` is still a
     `stat` call in plan-assembly** — so instead add
     `resource_sizes: tuple[tuple[str, int], ...]` (or a `dict`) to
     `SkillDescriptor`, populated in `_descriptor_for_root` / `load_skill` from
     the file list already walked (`f.stat().st_size`, no extra read beyond the
     `rglob` already done). `_select_skills` then reads it as pure metadata.
   - **Do NOT** add per-resource `sha256` in slice 2 — the whole-directory
     `content_sha256` (already on the plan item as `body_sha256`) is the
     integrity anchor, and `load_skill_resource` verifies against it. Per-
     resource digests are a later refinement if a consumer needs to verify a
     resource in isolation.
2. **`runtime/context_builder.py::_select_skills`** — in the `LOAD` branch,
   after the body attach: build `item["execution_resources"]` from
   `descriptor.script_paths` (kind `"script"`), `reference_paths`
   (`"reference"`), `example_paths` (`"example"`), `asset_paths` (`"asset"`),
   each `{"path", "kind", "bytes"}` from the descriptor's `resource_sizes`.
   Only when there is at least one such resource. **No content read.**
   `coverage["skill_execution_resources_listed"] = sum(1 for item in skills if
   item.get("execution_resources"))`.
3. **`runtime/flow_start.py`** — docstring only (mention the manifest is
   listed, content is not loaded).
4. **Tests** `tests/test_context_builder.py` + `tests/test_skills_format.py`:
   - a LOAD Skill with `scripts/x.sh` + `references/y.md` → plan item has
     `execution_resources` with both, correct `kind`/`bytes`, **no content
     key**;
   - a LOAD Skill with no resources → no `execution_resources` key;
   - a WITHHOLD / DENY Skill → no `execution_resources`;
   - `load_skill_resource(descriptor, "scripts/x.sh")` → exact bytes;
     `load_skill_resource(descriptor, "SKILL.md")` and `"../etc/passwd"` and
     `"nonexistent"` → `ValueError` / `SkillParseError`;
     post-discovery content change → `SkillChangedError`;
   - `coverage["skill_execution_resources_listed"]` counts correctly;
   - end-to-end `build_project_skill_catalog` + `build_context_plan`.
   - ≥5 mutations on `_select_skills`'s manifest branch + `load_skill_resource`
     path validation.
5. **`work/roadmaps/CAPABILITY_CHECKLIST.md`** — 6.9 / S6 (+ mention in 6.11)
   evidence clause: slice 2 lists execution resources for LOAD Skills and adds
   `load_skill_resource` as the deterministic single-file pull; **no content
   loaded in plan-assembly**; **no status flip** (6.9's DONE gate — the frozen
   selection eval / progressive-disclosure value shown — is unmet, and content
   is still pull-not-push).

## 4. Companion micro-slice (optional) — body byte-budget

Slice 1 attaches `item["body"]` **unconditionally** for a LOAD Skill. An
adversarially-large `SKILL.md` (the `assess_skill` gate flags
`SKILL_BODY_TOO_LARGE` at 32 KB as REVIEW, not BLOCK — so a 5 MB body on a
`VALIDATED` Skill still loads in full today). A ceiling —
`item["body"]` omitted with `item["body_withheld_reason"] =
"BODY_EXCEEDS_BUDGET"` above e.g. 64 KB — is a **restriction** on what
plan-assembly loads, not an expansion, and is the same shape as slice 1's
existing `body_withheld_reason` fail-closed path.

**Guardrail read:** wave12's clause is about `budget_class` *expanding* what is
fetched. A cap does the opposite. It is defensible without operator approval —
but because it is the *first* case of a size threshold changing plan content,
flag it for reviewer judgement; if a reviewer wants operator sign-off on the
ceiling value, that is a review comment, and the manifest slice (§3) ships
independently.

Recommend: **§3 is slice 2; §4 is an optional add to the same PR or a trivial
follow-up** — implementer/coordinator call.

## 6. Out of scope

- **Eager resource-content loading** into the plan — never (6.11 guardrail).
- **Per-resource `sha256`** in the descriptor / manifest — a later refinement;
  `content_sha256` + `load_skill_resource`'s whole-dir verification is
  sufficient for slice 2.
- **A `MAY_LOAD` budget tier** — still no data source (6.11 row); not this
  slice.
- **The frozen selection evaluation** that 6.9's promotion gate requires — a
  separate L4/EXP-B-adjacent effort, not a loading slice.
- **`THIRD_PARTY` Skills** — `build_project_skill_catalog` produces only
  `BUNDLED`; unchanged.
- **Executing or re-inspecting resources** — the `assess_skill` gate is the
  control (§1e).
- **MCP / tool resources** — different surface.

## 7. OPERATOR DECISION

**None.** Plan-assembly, `BUNDLED`, gate-passed Skills only, no content loaded,
no authority surface (§1e). The §4 body-ceiling value is a reviewer-judgement
call, not an operator decision.

## 8. STOP-condition check (dispatch)

- *The only real increment requires a retrieval/search mechanism?* — **No.**
  The manifest is a listing of already-declared paths; `load_skill_resource` is
  a deterministic single named-file read, the same shape as slice 1's body
  read. Neither is search.
- *Execution-level loading needs an authority decision (executable script
  content)?* — **No.** LOAD Skills already passed `assess_skill`'s static
  script inspection; slice 2 loads no content and executes nothing (§1e).
- *Slice 1's body-attach needs rework first?* — **No.** It is correct and slice
  2 sits cleanly after it in the same `LOAD` branch.

No STOP condition triggered. Slice 2 (§3) is dispatchable.
