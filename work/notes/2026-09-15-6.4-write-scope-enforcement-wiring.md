# 6.4: wiring `require_write_scope_binding` into `CanonicalRunGuard`

Roadmap 6.4. Direct follow-up to PR #362 (the opt-in flag, schema+API only)
and PR #361 (the `verify_git_run` fork/scoping note). Dispatched by
coordinator `venu`: "the actual guard reading `require_write_scope_binding`,
mirroring `_require_bound_worktree`'s enforcement pattern."

**No separate stop-and-ask design note** — per this dispatch's own explicit
branching ("if it's a clean new guard registration with no live-behavior
change ... you can likely go straight to implementation, your call"). This
note documents the reasoning and verification inline instead, since the
guard now reaches an already-fired event and that reasoning is worth a
durable record even when it doesn't need prior sign-off.

## Why this is safe to add directly (not the same situation as #361's fork)

`CanonicalRunGuard` is registered on already-fired events
(`RUN_STARTING`/`BEFORE_SEND`/`BEFORE_RESUME` are live via `maps run
send-context` and the `--enforce-canonical-run` recovery-tick path). Adding
a new check inside it is only safe if it cannot change behavior for any run
that did not explicitly ask for it — exactly the property PR #362 built:
`write_scope_binding_required` defaults `False`/absent-equivalent for
*every* run that doesn't pass `--require-write-scope-binding`, and as of
this PR, zero production call sites pass it. So:

- No existing run has the flag set → the new check reads
  `manifest.get("write_scope_binding_required")`, gets a falsy value, and
  returns `None` (allow) immediately — the exact same short-circuit shape
  `_require_bound_worktree` already uses for `manifest.get("worktree")`.
- This is unlike PR #361's fork (A) — enforcing against the *implicit
  default* `writable_scope` for every run regardless of opt-in — which
  would have changed live behavior. This wiring only ever fires for a run
  that named itself in scope, so there is nothing to flag before building.

## What changed

`runtime/policy/harness_guard.py`:

- `ChangedPathsSource` type alias + `changed_paths: ChangedPathsSource =
  collect_git_changes` constructor param, mirroring `worktree_identity`'s
  injectable-callable shape exactly (testability, no direct Git I/O import
  buried in a method body).
- `CanonicalRunSource` Protocol gains `verify_run_changes(...)` — the
  existing `TaskStore` method the advisory `run-verify-git` CLI already
  uses (`runtime/state/integrity.py::verify_run_changes`, itself unchanged
  by this PR — rule 12, no duplicate scope-comparison logic written here).
- `_require_write_scope(manifest, run_id)`: self-gates on the opt-in flag
  (return `None` immediately if unset); otherwise reads real changed paths
  via `self.changed_paths(repo_root, base_revision=...)`, denies
  `RUN_WRITE_SCOPE_UNAVAILABLE` if that raises `RuntimeError` (non-git repo
  etc., mirroring `_require_bound_worktree`'s `RUN_WORKTREE_UNAVAILABLE`
  handling), then calls `source.verify_run_changes(...)` and denies
  `RUN_WRITE_SCOPE_VIOLATION` naming the out-of-scope paths if not `ok`.
- Called from `__call__` only inside the `continuing` block (`start`/
  `send`/`resume`), right after `_require_bound_worktree`, **never**
  `SESSION_STOPPING` — same reasoning as the worktree seam's own explicit
  rule ("denying a stop because scope drifted would strand sessions").
- No `runtime/recovery/production.py` change needed: `CanonicalRunGuard`'s
  new capability is a constructor default (`collect_git_changes`), not a
  new composition-root wiring call — confirmed by an isolation test.

## Verification

`tests/test_harness_canonical_guard.py::WriteScopeGuardTests` (5 tests,
unit-level with a `FakeSource`): in-scope allow, out-of-scope deny, unreadable
Git changes deny, unbound run allows without ever calling the changed-paths
source (spy raises if called), stop is never denied by this check.

`tests/test_execution_integrity.py::IntegrityTests` (3 new tests, real
`TaskStore` + real `git init` repo, no mocks): `CanonicalRunGuard` composed
with the real store denies a real `resume`/`start` continuation when an
actual uncommitted change (`README.md`) lands outside the task's real
`writable_scope` (`["src"]`) with `guard_code=RUN_WRITE_SCOPE_VIOLATION`
naming the file; allows when the real change (`src/a.py`) is in scope;
allows an out-of-scope real change when the run never opted in
(`require_write_scope_binding` omitted) — proving the opt-in gate holds
end-to-end, not just against a fake.

`WriteScopeBindingFlagIsolationTest` updated (was asserting "no guard reads
this yet," now asserts "only `CanonicalRunGuard` reads it, nothing else in
`runtime/policy/` or `runtime/recovery/`") — this is an intentional,
by-design change to that test's assertion, not a regression: its whole
point was to catch premature/accidental wiring, and this PR is the
deliberate, scoped wiring it was written to eventually allow.

254 tests total green: the two files above (33 tests) plus every other file
referencing `CanonicalRunGuard`
(`test_agentic_security_baseline.py`, `test_agentic_security_hook_context.py`,
`test_cli_run.py`, `test_harness_service.py`,
`test_recovery_composition_root.py`, `test_recovery_external_effect_ambiguity.py`,
`test_recovery_production_trigger.py`, `test_recovery_supervisor.py`,
`test_run_session_lineage.py` — 201 tests, none of which set the new flag,
confirming zero behavior change for every existing fixture).

## What this does not do

- Does not compose or expose `require_write_scope_binding` from any real
  production dispatch path — no `maps flow start` caller in this codebase
  passes it yet. Same "no production exposure" gap this row's other guards
  went through before their own first-exposure exercises.
- Does not touch `verify_git_run`, `verify_run_changes`, or any scope
  storage/comparison logic — reused as-is.
- Does not add `AFTER_WRITE`/`BEFORE_WRITE` firing (that's PR #360's
  separate, still-unfired `WriteScopeGuard` track under this same row —
  a different mechanism, not superseded or touched by this one).
- Does not flip `CAPABILITY_CHECKLIST.md` row 6.4 to `DONE`: the guard now
  genuinely exists and is tested end-to-end, but has no production call
  site setting the flag, so it has not yet had a first real exposure the
  way the destructive-action guard or the 6.22 guard eventually did.
