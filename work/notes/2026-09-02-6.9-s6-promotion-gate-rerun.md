## 3. Is route (a) — further selector work — still open? **NO. It is blocked on §6.33.**

#260's review (luve, independent) established — and I re-verified against the
frozen corpus — that the two residual gaps cannot be closed lexically without
regressing an already-passing category:

- **VOCABULARY_SHIFT (`EXPB-V01`).** A plural/tense lemmatiser (the #250 §5(a)
  proposal) turns V01's only match into the single distinctive token
  `credential`→`credentials`, weight 1.0 — **lexically identical** to hard
  negatives `EXPB-H02` (`rotation`→`secrets-rotation`) and `EXPB-H03`
  (`api`→`api-contract-review`). Any strength floor low enough to admit V01
  re-admits H02/H03 → **HARD_NEGATIVE regresses** → violates §3 criterion 2.
  `V02`–`V04` require true synonymy (`brownout≈outage`, `soak≈load`,
  `payload shape≈contract`) — no morphological path at all.
- **AMBIGUOUS (`EXPB-A01`/`A02`).** Not score-ties: `A01`'s token evidence
  favours one Skill. A margin rule loose enough to flag A01 also flags
  `EXPB-M01`, a genuine legitimate multi-Skill tie → **MULTI_SKILL regresses
  from 1.00** → violates §3 criterion 2.

Both gaps require **query expansion / semantic similarity** — which is roadmap
**§6.33** (`EVIDENCE-GATED`; "Context Builder stays explicit-first"; its own
promotion gate: "a frozen evaluation … must demonstrate meaningful improvement
over explicit/baseline"). §6.33 is a *separate* roadmap item with a *separate*
evidence gate. Chasing it inside 6.9 would pre-empt that gate and is out of
scope. **So route (a) — "a reviewed `_select_skills` PR closing all 3 gaps" —
cannot be completed under the explicit-first constraint; it is blocked on §6.33
being built and promoted first.**

## 4. Does the selector now clear the promotion gate? (status-truth rule + §17.3)

Two readings, both stated honestly:

**The FLIP reading.** §6.9's *literal* Promotion gate is *"Do not rely on fuzzy
Skill selection without a frozen selection evaluation."* — the frozen eval
**exists** (EXP-B, sha-pinned, real harness), covers all six "must include"
categories with depth, and the fuzzy selection is no longer relied on blindly
(the match-strength gate + the documented eval characterize it). §6.9 is `P2`.
The residual is provably §6.33's domain, and the roadmap deliberately keeps
§6.9 explicit-first. On this reading the gate is met and 6.9/S6 could flip.

**The NO-FLIP reading (adopted).**

1. **#250 — a prior independent gate step — ruled that "0.00 on categories
   §6.9's own list enumerates" is not DONE**, and set §5(a)/(b) as the routes.
   #260 completed *part* of (a) (1 of 3 gaps). Per #250's own framing we are not
   at "(a) complete", and §3 above shows (a) *cannot* be completed under the
   explicit-first constraint. That leaves (b).
2. **§17.3 lists "explicit operator decision" as a distinct evidence type** —
   precisely the mechanism for "promote a capability with a characterized,
   accepted limitation." Whether synonym-shift and fine-grained-ambiguity
   routing are *inside* §6.9's DONE bar or belong to §6.33 is a **scope-boundary
   authority call**, not a code question. A reviewer resolving it unilaterally —
   especially by overriding a prior NO-FLIP on the "literal gate is met"
   technicality — is the pattern the trajectory status-truth rule guards against
   ("do not let … an unsupported summary … become program truth").
3. The safety argument is already bounded elsewhere (6.22 trust gate + SEC4
   quarantine sit after selection), so nothing is *unsafe* about the current
   state — but 6.9 is the routing-*correctness* capability, and two of its six
   evaluation categories score zero. That is a real, measured limitation the
   operator should sign off on explicitly, not one a reviewer should wave
   through.

**Verdict: NO FLIP.** The gate is now *one operator decision away* from DONE —
route (a) is exhausted/§6.33-blocked, so **path (b) is the sole route**, and it
is a clean, well-supported decision for the operator to make.
