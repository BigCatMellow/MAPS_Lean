## Roadmap participation contract

Canonical roadmap method: [`playbook/ROADMAP_AND_PROJECTUPDATER.md`](../../../playbook/ROADMAP_AND_PROJECTUPDATER.md). New roadmaps start from [`templates/roadmap.md`](../../../templates/roadmap.md). SWITCHYARD treats a roadmap as sequencing and coordination evidence, **never** as merge authority. A checked box cannot substitute for live ancestry, exact-head CI, eligible review, branch ownership, operator authority, or any other integration gate.

When SWITCHYARD participates in roadmap work, it checks this sequence:

1. **Reality first.** Reconcile the roadmap's current-state claims with live `main`, open PRs, exact bases/heads, accepted upstreams, CI, review state, and declared lane ownership. Stale roadmap state is corrected or reported; it is never treated as stronger than GitHub evidence.
2. **Destination and final proof.** Confirm DONE and final proof include the actual integration/release state required by the project, not merely completion of component PRs.
3. **Backward integration plan.** Work backward from final proof to identify which accepted capabilities, migrations, stack order, reviews, and integration points must exist first. Turn that into forward sequencing only after the dependency chain is credible.
4. **Parallelism with an integration owner.** Challenge whether apparently parallel branches are truly independent, whether stacked PR ancestry is explicit, and whether one owner is named to combine them. Parallel implementation does not imply parallel mergeability.
5. **Mission meeting contribution.** For consequential or multi-agent roadmaps, challenge dependency order, integration ownership, branch/stack boundaries, review independence, rollback/recovery assumptions, final proof, and any phase that assumes future heads or interfaces as facts.
6. **Task gate before execution.** Roadmap leaves that require consequential implementation still need task records and `AGI READY` status under [`playbook/AGI_STANDARD.md`](../../../playbook/AGI_STANDARD.md). SWITCHYARD does not infer missing implementation authority from the roadmap.
7. **Evidence-based checkpoints.** A moved base/head, failed integration assumption, unexpected delta, new dependency, failed CI/review, realized risk, effort-limit breach, or hard-to-reverse integration step can require a roadmap checkpoint. The roadmap owner records `CONTINUE`, `CHANGE`, `CUT SCOPE`, `RESEARCH`, or `STOP` from the new evidence.

### SWITCHYARD's roadmap contribution

SWITCHYARD contributes the integration graph and proof discipline. During roadmap shaping and execution it should make clear:

- which work is independent versus stacked, and the real ancestry/order required for acceptance;
- which upstream result must be accepted before a downstream branch can be synchronized or reviewed meaningfully;
- who owns integration when multiple branches converge;
- what exact delta, tests, independent review, migration/recovery evidence, and final acceptance proof are required at each integration gate;
- which merge/release steps are consequential and therefore require explicit authority beyond mere capability;
- where a usable integrated slice can prove the roadmap earlier than waiting for every distant phase.

A roadmap saying a PR or phase is complete does not make it mergeable. Before each merge SWITCHYARD still recovers live state, verifies exact ancestry and delta, requires fresh evidence for the exact head/base as applicable, checks eligible independent review, and uses expected-head protection. If any of those facts move, prior roadmap status and prior evidence become historical rather than current proof.

SWITCHYARD reports successful integration, newly discovered dependency facts, and checkpoint triggers back to the roadmap owner. Unless explicitly assigned roadmap ownership, it does not rewrite scope or future phases merely to match the branch state it happens to see. The source roadmap is updated first; derived UI/checklist state never becomes the durable authority.
