## Hard counterarguments

1. **MAPS_L already has a planning method.** Harada recursive branching may be mostly naming and packaging. The cost of 14 branch files and index maintenance can exceed its marginal insight. A credible review should be free to recommend retaining only a few targeted changes.
2. **The new goal may look like a second master roadmap.** This research package must not compete with accepted master authority. Until adoption, [master](../00-MASTER-MAPS-CAPABILITY-ROADMAP.md) remains accepted planning orientation and this is a proposal. If approved, collapse duplicate normative material by routing from the canonical master to one owner; don't keep two equally authoritative masters indefinitely.
3. **Nine branches could be a decorative Harada grid.** Nine were chosen to match meaningful MAPS_L domains, *not* to satisfy the Harada form. Challenge each root as a distinct necessary outcome; combine/split if evidence warrants.
4. **An external-pilot-first priority can hide critical gaps.** H08.3 is useful integration proof, but not a waiver for H04/H06 trust boundaries. A pilot with no recovery cannot prove general recovery; a pilot with simple tools cannot prove all external-effect controls.
5. **A full destination proof can itself cause perfectionism.** Use precise minimum proof for current wave; don't block a sound external pilot on hypothetical fleet management or unneeded snapshots.
6. **"DONE" is not "works on every real caller."** H4/E5/SEC3 and L6 demonstrate why methodical evidence checking matters more than moving green checkboxes into a diagram.
7. **An implementation-first PR can overfit evidence.** New test design should freeze behavior before changing it; use risk-appropriate independent review, not post-hoc completion prose.

## Proposed experiment for method value (not executed)

On a representative, frozen set of MAPS_L planning questions with easy/complex/blocked cases:
- **Control:** existing [master](../00-MASTER-MAPS-CAPABILITY-ROADMAP.md) + [checklist](../CAPABILITY_CHECKLIST.md) + [Project Bootstrap](../../playbook/PROJECT_BOOTSTRAP.md).
- **Candidate:** this one-hop index + recursive condition ownership + dependencies, with equal permitted source access and budget.
- **Outputs:** omissions detected, correct prioritized next action, invented tasks, source/authority errors, navigation steps, context/cost, reviewer agreement, and stable result after a branch update.
- **Outcome:** adopt only the pieces that show useful benefit; otherwise **NO CHANGE** or narrow to a navigation pattern.

No formal scientific improvement claim may be made from this single author-driven remap. Independent review must validate logical and source correctness; optional empirical comparison may separately validate method benefit.

## Immediate known unknowns to preserve

- Live accepted production deployment and task outcomes beyond the current dated source snapshot.
- Which specific actions and tool effects would be exercised by the first approved external target.
- Whether every currently operational resume/call site is guarded by the intended hook.
- Whether the source checklist's L6 DONE label can be reconciled with absent real-run manifest config hash.
- Whether a fresh reader would actually navigate faster using this structure than old Bootstrap.
- Whether all 35 old master capabilities remain relevant to a chosen current outcome.

**Result of this author challenge:** the full recursive roadmap is a plausible *candidate representation*, not itself evidence of superior planning or permission to execute the entire feature inventory.
