### H03.3.1 — Identify the mutation that must be validated
Pick a representative bounded write (for example a source change subject to syntax/test checks). Record the exact before/after operation and expected cheap checker.

### H03.3.2 — Validate *near the effect*, not only before a future resume
- Existing `EnvironmentSpec.validation` tiers and validation callback factory exist.
- A recovery `quick` tier can run through opt-in `maps recovery-tick --repo-root`.
- `--enforce-validation` provides an opt-in pre-resume blocking slice for concrete failures; absent opt-in some checks are advisory.
- The full **immediate post-mutation** exit criterion is not yet demonstrated on representative production paths.

### H03.3.3 — Separate validation findings from authority
Only canonical task/policy/approved hook paths may block/permit work. A passed validator never grants missing authority. UNKNOWN, timeout and skipped checks require explicit policy-driven handling, not assumed success.

### H03.3.4 — Verify failure and recovery
Reproduce: valid mutation passes; a bad mutation is detected promptly; skipped/unavailable checker yields explicit evidence; repair and retry remain bounded; no duplicate external effect. Add a focused regression test after a recurring defect.

### H03.3.5 — Promotion proof
One real operation path demonstrates enforcement at the intended timing, low false positives, bounded cost, unchanged authorization, and reproducible tests. **Do not mark H4 fully DONE from an opt-in pre-resume-only demonstration.**
