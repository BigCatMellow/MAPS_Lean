## Item 6: false-negative risk in `touches_canonical_paths()` — REQUIRED finding

Real gap found. `CANONICAL_FILENAME_RE` matches only `AGENTS.md`,
`CLAUDE.md`, or `*_SYSTEM.md`. But `MAP_System/` has several root-level
docs that are unambiguously canonical policy/governance files by the same
standard CHANGE_CONTROL_SYSTEM.md itself uses (cross-referenced from
`DECISION_AUTHORITY_SYSTEM.md`, `RISK_SYSTEM.md`, `SECURITY_PERMISSIONS_SYSTEM.md`,
and this very file) but do not match the naming convention and are not
under `shared/`/`templates/`:

- `MAP_System/DECISION_CLASSES.md`
- `MAP_System/DESTRUCTIVE_ACTION_POLICY.md`
- `MAP_System/AGENT_PERMISSION_LEVELS.md`
- `MAP_System/NEW_PROJECT_WIZARD.md`

A future task whose `output_paths` touches only one of these files, with no
`risk_class`/`risk_severity`/`task_tier` set (true of most of the
pre-TASK-277 task population, confirmed live: many released tasks above
have all three `None`), would classify `"low"` and release with only the
Emergence checkbox — even though it edited the document that defines when
destructive-action approval or operator-tier approval is required. That is
exactly the class of gap this task exists to close.

**No live misclassification occurred**: I checked every `task_output_paths`
row repo-wide for these four filenames (`TASK-108`, `TASK-112`, `TASK-115`,
`TASK-126`, `TASK-174`). Only `TASK-174` is in the current backlog, and it
also touches `ARCHIVE_RETENTION_SYSTEM.md`/`CHANGE_CONTROL_SYSTEM.md`/etc.,
so it is independently caught by the `*_SYSTEM.md` branch and correctly
held back regardless of this gap. The other three are already
`RELEASED`/historical and predate this rule. So this is a latent risk, not
a shipped defect — but it will bite the next task that touches
`DESTRUCTIVE_ACTION_POLICY.md` alone.

**Required action**: extend `CANONICAL_FILENAME_RE` (or replace the
naming-convention heuristic with an explicit canonical-file list/registry)
to cover these four files, or state affirmatively in
`CHANGE_CONTROL_SYSTEM.md` why they are intentionally excluded. Given how
directly `DESTRUCTIVE_ACTION_POLICY.md` and `DECISION_CLASSES.md` gate
other approval machinery, silence here is not a safe default.

Other parts of item 6 checked clean: the `shared`/`templates` segment
check is path-position-based, not root-anchored, so it already covers a
nested `shared/` anywhere (confirmed live via TASK-271's
`templates/install/bin/...` and TASK-053's non-`MAP_System` canonical

## Item 7: is DEC-032's framing honest, and is the rule mechanically derivable rather than a fresh judgment call?

Yes to both, with one adjacent (pre-existing, out-of-scope) note.

DEC-032's text explicitly states it "does not pre-decide the rule's
content — that is TASK-288's acceptance criteria to satisfy and a
reviewer's to verify," and grants execution authority, not content
authority. That framing holds up: the canonical-path branch is a direct
restatement of `CHANGE_CONTROL_SYSTEM.md`'s pre-existing wording, not a new
invention (setting aside the item-6 gap above, which is an
under-coverage bug in an old rule, not a new judgment call). The
`risk_class=SECURITY` / `risk_severity in {STRUCTURAL,BLOCKING}` branch
maps directly onto `RISK_SYSTEM.md`'s pre-existing definitions (line 37:
SECURITY = "trust boundaries, injection, auth, CSRF, secrets"; lines 52-53:
BLOCKING = "actively exploitable," STRUCTURAL = "touches authority,
security boundary, or irreversible action") — this is the same taxonomy
`review-guide.md`'s High-risk prose category already describes, just
addressed by its existing structured fields instead of restated in prose.
The `task_tier in {policy, operator, architecture}` branch matches how
`pre_dispatch_policy.py` (line 214, 404, 388) already treats those same
three values as requiring elevated approval, and `"bounded"`/`"mechanical"`
as the low-friction defaults — so `classify_release()` is consistent with
the *actual, already-live* enum usage elsewhere in the system, not an
invented one.

**Adjacent, non-blocking note**: `ORCHESTRATION_ENTRYPOINT_SYSTEM.md` (line
70) documents a *different* `task_tier` enum (`shaping, local, core,
helper, approval`) that does not match either `pre_dispatch_policy.py`'s
real usage or the live data in `tasks.task_tier` (`policy`, `operator`,
`architecture`, `bounded`, `mechanical` all appear in the DB). This is a
pre-existing doc/reality mismatch that predates TASK-288, is not in its
`output_paths`, and does not affect `classify_release()`'s correctness
(which correctly follows the live enum). Flagging as a RECOMMENDED
follow-up, not a TASK-288 defect.
